## Tier 1 — high leverage, low effort (do next sprint)

### 1. Auto-cancel for STARTING state

#### What we see today
We already configured a 30-min RUNNABLE → CANCEL on `biomate-nextflow-queue` (2026-06-04). That catches the routing class of bugs. But STARTING is a separate failure mode:

- ECR pull rate-limit → image pull hangs → STARTING for hours
- Broken image manifest (we just pushed 10 new ones — `biomate/<name>-nf:1.0`) → infinite retry loop
- ENI/networking issue → container can't start, but Batch never marks it failed

A job stuck in STARTING for 30+ minutes is almost certainly broken.

#### Proposal
Add a second action to the existing `jobStateTimeLimitActions`:

```bash
aws batch update-job-queue --job-queue biomate-nextflow-queue --region us-west-2 \
  --job-state-time-limit-actions '[
    {"state": "RUNNABLE", "maxTimeSeconds": 1800, "action": "CANCEL",
     "reason": "MISCONFIGURATION:JOB_RESOURCE_REQUIREMENT"},
    {"state": "STARTING", "maxTimeSeconds": 900, "action": "CANCEL",
     "reason": "MISCONFIGURATION:CONTAINER_LAUNCH_TIMEOUT"}
  ]'
```

Apply to every queue (CPU + GPU + HPC).

#### Effort
S — one CLI command per queue.

#### Risk / cost
- False positives if Batch is genuinely slow during legit high-load periods. Mitigation: the 15-min STARTING max is generous. Image pulls for our largest images (4 GB GPU) take ~3 min on a fresh instance.
- Cost: $0.

#### Open questions
- Is 900s the right STARTING threshold? Image-pull profile would say.
- Do we want a CloudWatch event on auto-cancel so we know the system is being self-corrected (vs silent)?

### 2. Job retry policy with selective `evaluateOnExit`

#### What we see today
Every BioMate Batch job has `attempts: []` — single attempt, no retry. When Spot reclaims a g4dn mid-run, when ECR has a transient 503, when ECS service has a brief blip, the job fails permanently and the workflow has to be re-run from scratch by the user.

Per-Nextflow run history on dev: 2026-06-04 alone had ~5 jobs fail with reasons "Host EC2 instance was terminated", "ECS task event stop", "DockerTimeoutError on Pull". All transient. All re-runnable.

#### Proposal
The job definitions are auto-generated by Nextflow per-image, but we generate the executor config that controls retry semantics. In `backend/lib/galaxy/webapps/galaxy/api/nextflow_executor.py` add to the per-process Nextflow config:

```groovy
process {
    errorStrategy = { task.attempt <= 2 ? 'retry' : 'terminate' }
    maxRetries = 2
    // Only retry on transient failures, not on workflow errors (exit != 0):
    errorStrategy = { task.exitStatus in [137,143,255] ? 'retry' : 'terminate' }
    // 137 = SIGKILL (Spot reclaim), 143 = SIGTERM (ECS graceful stop), 255 = container died
}
```

Alternatively, configure at the Batch job-definition level via `retryStrategy`:

```json
{
  "attempts": 3,
  "evaluateOnExit": [
    {"action": "RETRY", "onStatusReason": "Host EC2*"},
    {"action": "RETRY", "onStatusReason": "DockerTimeoutError*"},
    {"action": "EXIT", "onStatusReason": "*"}
  ]
}
```

The Batch-side approach is cleaner because it handles infrastructure failures Nextflow can't see (e.g. Spot reclaim during image pull, before the workflow code even runs).

#### Effort
M — generate `retryStrategy` in the per-image job def at register time (Nextflow does this lazily), or patch them after creation via `aws batch register-job-definition`.

#### Risk / cost
- Cost increase if non-transient failures are retried (we'd pay 3× for a workflow with a real bug). Mitigation: `evaluateOnExit` is exact, retry only on infra-class status reasons.
- Latency: a retried Spot reclaim adds ~3 min (new instance + image pull) per attempt. Acceptable.

#### Open questions
- Should the retry budget be per workflow (user can override?) or per-deployment uniform?
- Should we surface "retried 1× due to Spot reclaim" in the Galaxy UI run timeline so users see what happened?

### 3. publishDir-failure recovery sweep

#### What we see today
This is the recurring **JVM SIGSEGV in `PublishDir-X` / `S3TransferManager.<init>`** on Debian trixie glibc 2.41 + OpenJDK 21.0.11. Pattern from smoke run `5e7a2c52` (2026-06-04):

```
23:05:04.784  Task COMPLETED, exit: 0          ← Batch task succeeded
23:05:05.473  [TaskFinalizer-1] Creating thread pool 'PublishDir'
23:05:05.709  [PublishDir-3] Creating thread pool 'S3TransferManager'
              JVM SIGSEGV → hs_err_pid448.log
```

Net result:
- Batch task succeeded; all 4 expected output files live in `s3://.../work/<hash>/...`
- `s3://.../outputs/<run_id>/` has only the empty directory marker
- Galaxy reports `status: interrupted, returncode: -6`
- User sees "failed" workflow; downloads don't work

The CRT mitigation flags (`-Xss2m`, `-Daws.crt.disable.crt.in.client=true`, per-run cache, `LD_BIND_NOW=1`) plus the NXF_VER pin to 25.10.5 reduce the frequency but don't eliminate the crash — it's an upstream glibc/JDK/CRT bug we can't fix in this codebase.

#### Proposal
**Recovery, not prevention.** When Galaxy detects `status=interrupted && returncode=-6` AND the underlying Batch task succeeded (parseable from `workflow-trace.txt`), run a post-mortem sync:

```python
# new function in nextflow_executor.py
def _recover_publishdir_after_jvm_crash(run_id: str, log_dir: Path):
    trace_path = log_dir / "workflow-trace.txt"
    if not trace_path.exists():
        return False
    # Parse trace for COMPLETED rows
    completed_tasks = []
    for row in csv.DictReader(trace_path.open(), delimiter="\t"):
        if row.get("status") == "COMPLETED" and row.get("exit") == "0":
            completed_tasks.append(row)
    if not completed_tasks:
        return False
    # For each completed task, sync work/<hash>/<files> to outputs/<run_id>/<process_name>/
    for task in completed_tasks:
        work_path = task["hash"]  # e.g. "8f/0abf58..."
        process_name = task["name"].split("(")[0].strip()  # e.g. "TRANSCRIPTOMIC_MOA_LINCS"
        # Use aws s3 sync, excluding .command.* and .exitcode internals
        subprocess.run([
            "aws", "s3", "sync",
            f"s3://{WORK_BUCKET}/nextflow/work/{user_id}/{run_id}/{work_path}/",
            f"s3://{WORK_BUCKET}/nextflow/outputs/{user_id}/{run_id}/{process_name}/",
            "--exclude", ".command.*", "--exclude", ".exitcode",
        ], check=True)
    # Update Galaxy run status to completed (with note: "recovered from publishDir JVM crash")
    return True
```

Wire it into `_finalize_nextflow_run()` between the JVM-exit detection and the status update.

#### Effort
M — ~150 LOC + one integration test that simulates a `hs_err` file + verifies sync runs.

#### Risk / cost
- Risk: false-positive recovery if `workflow-trace.txt` shows COMPLETED but the actual outputs are missing/partial. Mitigation: verify expected output files exist in `work/` before sync.
- Cost: each recovery adds one `aws s3 sync` (~1 s per task in same region). Negligible.

#### Open questions
- Should the recovered status be `completed` or a new `completed_with_recovery` so we can track the upstream-bug incidence?
- Does this make the user-facing UI less aware of when the JVM crash is happening? (Pro: stops complaints; Con: hides the upstream issue from prioritization signals.)

### 4. CloudWatch dashboard for Batch queue health

#### What we see today
We discovered the 25-min RUNNABLE stall by manually polling `aws batch list-jobs` after a smoke run failed. There's no proactive signal that the queue is degraded. Same for image-pull stalls, spot-reclaim storms, and CE auto-scaling lag.

#### Proposal
Three CloudWatch metrics, one dashboard:

| Metric | Source | Threshold | Why |
|---|---|---|---|
| `JobQueueDepth` (RUNNABLE + STARTING) per queue | Batch CloudWatch | alarm at > 20 sustained 5 min | Catches FIFO stalls + ECR rate-limits |
| `p95 SUBMITTED → RUNNING latency` per queue | Custom from EventBridge events | alarm at > 300 s sustained 5 min | Catches the actual user-facing slowness |
| `% of jobs SUCCEEDED vs FAILED` rolling 1-hour | Same EventBridge stream | alarm if < 80 % | Catches systemic failure mode (broken image, IAM regression) |

EventBridge already publishes job state changes per [BatchJobStateChange schema](https://docs.aws.amazon.com/batch/latest/userguide/batch_cwe_events.html). Pipe into a small Lambda → CloudWatch custom metric. Lambda is ~30 LOC.

#### Effort
M — Lambda (30 LOC) + CloudWatch dashboard JSON (15 metrics) + SNS topic for alarms.

#### Risk / cost
- Lambda costs ~$1/month at our job volume.
- Custom metrics ~$3/month (3 metrics × 6 queues × $0.30).
- Risk: alarm fatigue if thresholds are too tight. Start conservative.

#### Open questions
- Where do alarms route? PagerDuty? Slack #ops? Dev mailing list?
- Should we add a "BioMate dashboard health" panel to the existing admin UI so the team sees this in-product, not just in AWS Console?

## Tier 2 — meaningful, medium effort (backlog)

### 5. Per-workflow ECR image pre-pull

#### What we see today
First-time pull of `biomate/transcriptformer-gpu-nf:1.0` (~5 GB) on a fresh g4dn.xlarge takes 60–180 s. AWS Batch counts this against the `STARTING` state. For the most common workflows, this is repeated overhead.

#### Proposal
Custom AMI baked from the Batch ECS-Optimized AMI, with the most-used images pre-pulled at build time:

```bash
# in packer / EC2 Image Builder
docker pull 399683337364.dkr.ecr.us-west-2.amazonaws.com/biomate/biomni-tools:x86
docker pull 399683337364.dkr.ecr.us-west-2.amazonaws.com/biomate/biomni-admet:x86
docker pull 399683337364.dkr.ecr.us-west-2.amazonaws.com/biomate/transcriptomic-moa-lincs-nf:1.0
# … pre-pull the top-10 most-used by job-volume
```

Set the CE's launch template to the new AMI. Re-bake monthly or on major image push.

Alternative: pull-through cache via `docker-registry-cache` on each instance — more complex but auto-tracks new images.

#### Effort
M — image-builder pipeline + AMI publishing.

#### Risk / cost
- AMI staleness: if we update `biomni-admet` but the AMI hasn't been re-baked, Batch still pulls the new layer (incremental, fast). OK.
- AMI cost: ~50 GB EBS snapshot ≈ $5/mo.

#### Open questions
- Which 10 images do we bake in? Use job-history analytics to pick.
- Do we want the AMI build to be automated on every `biomate/*-nf` ECR push, or batched weekly?

### 6. Mixed Spot + On-Demand allocation for GPU CEs

#### What we see today
`biomate-gpu-spot-v1` is 100% Spot. Spot reclaim during a 35-min CryoSPARC SPA run = lose 35 min of work + a frustrated user. Job-retry policy (#2) helps but doesn't help GPU which often has limited Spot capacity.

#### Proposal
Change the CE's `allocationStrategy` to `SPOT_CAPACITY_OPTIMIZED` (already there) AND add a sibling On-Demand CE attached to the same queue at order=2:

```bash
aws batch update-job-queue --job-queue biomate-gpu-spot-queue --region us-west-2 \
  --compute-environment-order \
    'order=1,computeEnvironment=biomate-gpu-spot-v1' \
    'order=2,computeEnvironment=biomate-gpu-ondemand-v1'  # NEW
```

Result: Spot first (cheap), On-Demand fallback (reliable). User pays ~2× for the fallback but only when Spot is depleted.

#### Effort
M — create On-Demand CE (CloudFormation or Terraform) + attach to queue.

#### Risk / cost
- Cost depends on Spot interruption rate. At our scale, expect ~10 % of GPU minutes on On-Demand. Annual delta ≈ +$500.
- Risk: none if On-Demand fallback is well-sized (start with maxVcpus=64).

#### Open questions
- Bid percentage on Spot side: 70% or 100%?
- Does CryoSPARC need a fully on-demand queue option for production-critical runs?

### 7. Multi-AZ subnets in CEs

#### What we see today
Most CEs are configured with subnets in 1–2 AZs. Spot pool depletion is AZ-correlated — when one AZ runs out of g4dn capacity, our jobs sit RUNNABLE even though another AZ has capacity.

#### Proposal
Edit each CE to include subnets in all 4 us-west-2 AZs (a, b, c, d). Batch will scatter EC2 launches across AZs to pick up whichever has capacity.

#### Effort
S — one CE config edit per CE.

#### Risk / cost
- Cost: none.
- Risk: S3 access across AZs adds ~1 ms latency. Negligible.

#### Open questions
- Are there workflows whose performance is AZ-sensitive (e.g. accessing an AZ-local cache)? None known to me.

### 8. CE redundancy per queue

#### What we see today
`biomate-nextflow-queue` routes only to `biomate-nextflow-ce-v2`. If that CE goes VALID → INVALID (IAM rotation, AMI deletion, instance-role bug), the entire queue stalls silently. Other CEs already exist (`biomate-nextflow-cpu-v5`, etc.) but are unattached.

#### Proposal
Attach `biomate-nextflow-cpu-v5` as a second CE on `biomate-nextflow-queue` with `order=2`. Batch fails over automatically when order=1 can't satisfy.

```bash
aws batch update-job-queue --job-queue biomate-nextflow-queue --region us-west-2 \
  --compute-environment-order \
    'order=1,computeEnvironment=biomate-nextflow-ce-v2' \
    'order=2,computeEnvironment=biomate-nextflow-cpu-v5'
```

#### Effort
S — one CLI command. CEs already exist.

#### Risk / cost
- Cost: none unless order=2 starts seeing real load. (And if it does, that's the redundancy doing its job.)
- Risk: if the two CEs have different instance types, performance characteristics differ between order-1 and order-2 jobs. Document for users.

#### Open questions
- Do all the CPU CEs use the same AMI and instance role? Should they?

## Tier 3 — strategic, larger effort (quarterly planning)

### 9. Separate queue per workflow class

#### What we see today
Everything submits to `biomate-nextflow-queue` (or `biomate-gpu-spot-queue` for GPU after today's fix). Inside that queue is a mix of:

- Fast jobs: 5-s pharmacology models, 30-s ADMET predictions.
- Medium jobs: 5-min RNA-seq Salmon alignment, 10-min DESeq2.
- Slow jobs: 35-min CryoSPARC SPA, 2-hour MD simulation.

Same queue means a fast ADMET job can sit behind a slow CryoSPARC RUNNABLE simply because of FIFO ordering. Worse, the auto-cancel timeout has to be set for the slowest job's launch time, so misrouted fast jobs sit longer than necessary.

#### Proposal
Three queues per executor type:

| Queue | maxJobDuration | Auto-cancel RUNNABLE | Auto-cancel STARTING | Primary CE |
|---|---|---|---|---|
| `biomate-nextflow-light-queue` | 5 min | 5 min | 5 min | c5.large + c5.xlarge |
| `biomate-nextflow-heavy-queue` | 6 h | 30 min | 15 min | m5.4xlarge + r5.4xlarge |
| `biomate-nextflow-gpu-queue` | 6 h | 30 min | 30 min | g4dn.xlarge + g5.xlarge |

`nextflow_executor.py` chooses the queue based on the workflow's process labels or a per-workflow annotation in the workflow registry.

#### Effort
L — workflow-registry annotation + executor config generator + 6 new CEs + 3 new queues.

#### Risk / cost
- Cost: same compute, just better-organized. No infra cost change.
- Risk: misclassification → wrong queue → either too-tight timeout (fast queue) or unnecessarily long wait (heavy queue). Mitigation: start with a permissive default (heavy queue) and migrate workflows in batches.

#### Open questions
- Where does the queue-class annotation live? Workflow YAML? `nextflow.config`? Database table?
- Do users get to override the queue from the UI for a specific run?

### 10. **Eliminate publishDir entirely** — emit to `work/` only

#### What we see today
The recurring JVM SIGSEGV at `S3TransferManager.<init>` is fundamentally an upstream bug (glibc 2.41 + JDK 21 + AWS CRT native lib). We've now applied **6 mitigations** that each reduced but didn't eliminate the crash:

1. Per-run CRT cache (`-Daws.crt.lib.dir`)
2. Disable in-client CRT (`-Daws.crt.disable.crt.in.client=true`)
3. Stack size bump (`-Xss2m`)
4. FD-decouple subprocess (commit `41181b086`)
5. NXF_VER pin to 25.10.5 (avoid 26.04 CRT-default switch)
6. `LD_BIND_NOW=1` (force eager symbol resolution)

We're nibbling at an upstream issue we don't own.

#### Proposal
Stop using publishDir to S3. The Galaxy backend already has a `run:<runId>:datasets` virtual-history URI scheme (`routes.ts:2898`) that lists files from a run's `work/` directory directly. Use that as the canonical output source.

Two phases:

**Phase A — make publishDir optional in `nextflow.config`:**

```groovy
process {
    publishDir = []  // disable publish; outputs stay in work/
}
```

Galaxy already knows how to read from `work/`. The `/api/galaxy/histories/run:<id>/datasets` endpoint already does it.

**Phase B — backfill the agent context (Connection 3 from the History handoff):**

The `list_run_outputs` tool (already shipped) returns `run:<id>:outputs/<file>` URIs. Change them to `run:<id>:work/<task-hash>/<file>` since that's where files live. Backend resolver in `routes.ts` already supports both.

#### Effort
L — config generator change + agent context backfill + UI download-link backfill + migration plan (how do existing runs' presigned-URL links keep working?).

#### Risk / cost
- Removes one chronic failure class permanently. ROI is high.
- Risk: any consumer expecting files in `outputs/` paths (download links, S3 sync scripts, billing reconciliation) breaks. Audit needed.
- Cost: storage shifts from `outputs/` (cleaned by lifecycle rule) to `work/` (also cleaned by lifecycle rule, but Nextflow may treat them as cacheable). Need lifecycle policy review.

#### Open questions
- Does Nextflow guarantee `work/` is preserved on workflow success when `--resume` isn't used? (Yes per docs, but verify.)
- Do users' direct S3 download links (presigned URLs to `outputs/<path>`) break? How do we migrate them?
- This eliminates a 6-mitigation-deep workaround pile. Is the team ready for the migration cost?

### 11. Per-workflow cost / time observability

#### What we see today
Lago tracks vCPU-hour billing per user. Internally we have no visibility into:

- "What's the avg + p95 runtime per workflow?"
- "What's the avg + p95 cost per workflow run?"
- "Is `cryosparc_standard_spa` 10× more expensive than `rnaseq_deseq2`? Is that pricing communicated to users?"

This blocks informed decisions about routing, quota policy, and product pricing.

#### Proposal
EventBridge → Lambda → DynamoDB rolling stats:

| Workflow | Runs (7d) | p50 dur | p95 dur | p50 cost | p95 cost | Success rate |
|---|---|---|---|---|---|---|
| cryosparc_standard_spa | 47 | 32 m | 51 m | $0.96 | $1.78 | 89% |
| admet_pred_v2 | 1903 | 8 s | 22 s | $0.001 | $0.003 | 99.7% |
| rnaseq_salmon_quant | 412 | 4 m | 11 m | $0.12 | $0.34 | 96% |

Surface in admin UI panel + use for:
- Per-workflow capacity planning (do we need more GPU CE for cryosparc?)
- User pricing tier decisions (free tier capped at 10 cryosparc runs/mo?)
- Workflow regression detection (cryosparc avg ran 25 % slower this week — investigate)

#### Effort
L — EventBridge + Lambda + DynamoDB + admin panel.

#### Risk / cost
- Lambda + DynamoDB ≈ $20/month at our volume.
- Risk: latency-sensitive billing edge cases if the stats lag. Use eventually-consistent semantics; reconcile nightly.

#### Open questions
- Is this admin-only or user-facing too? ("My ADMET runs avg 8 s — am I being charged fairly?")
- Where does this fit relative to the existing Lago / Java billing service?

### 12. NF version pin self-test on Galaxy boot

#### What we see today
Today's pre-mortem found Nextflow had silently drifted from 25.10.5 to 26.04.2 (per the survey agent's report). Cause: `sync_to_dev.sh`'s version check had a Permission Denied that masked the drift; the launcher then downloaded "latest" = 26.04. The 26.04 line switched the default S3 client to CRT-only, exposing every BioMate user to the JVM SIGSEGV.

This is the third time the NXF_VER pin has been silently stripped. Each time, it took hours to diagnose because Galaxy looked healthy and individual runs looked normal — the drift only manifested under specific load patterns.

#### Proposal
Add a Galaxy startup health check:

```python
# new in galaxyctl health-check
def check_nextflow_version():
    expected = "25.10.5"
    actual = subprocess.run(["nextflow", "-version"], capture_output=True, text=True).stdout
    if expected not in actual:
        raise RuntimeError(
            f"Nextflow version drift detected: expected {expected}, got {actual!r}. "
            f"BioMate is incompatible with NF 26.x (CRT-default S3 client triggers JVM SIGSEGV). "
            f"Refusing to start. Set NXF_VER={expected} and re-deploy."
        )
```

Galaxy fails health check loudly. Container restarts visibly until fixed. Drift can't hide.

Plus: a CI test that asserts the pin survives `scripts/sync_to_dev.sh`:

```python
# new in backend/tests/test_nextflow_executor_nxf_ver_pin.py
def test_nxf_ver_pin_present():
    src = Path("backend/lib/galaxy/webapps/galaxy/api/nextflow_executor.py").read_text()
    assert 'env["NXF_VER"] = "25.10.5"' in src, (
        "NXF_VER pin stripped — this has happened 5 times historically. "
        "Restore the pin in _sanitize_subprocess_env(). "
        "See docs/20260601_NEXTFLOW_VERSION_DRIFT.md."
    )
```

#### Effort
S — boot check (~30 LOC) + CI test (~10 LOC).

#### Risk / cost
- Risk: Galaxy fails to boot if NF binary missing or wrong version → service outage. Mitigation: this is intended behavior. Better to fail fast than silently degrade.
- Cost: $0.

#### Open questions
- Should the boot check also assert the nf-amazon plugin version (3.4.4)?
- Should we monitor NF version on production via a CloudWatch metric so we see drift even between deployments?
