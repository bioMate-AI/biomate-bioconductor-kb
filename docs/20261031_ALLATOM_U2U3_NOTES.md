## 1. What was built
- `preference_updater.py` (U3): rank-based group advantage (ties averaged, no division by std); `GradedPreferenceUpdater.make_pairs` (groups need >= `group_size` valid members and non-trivial spread, dropped groups are counted; DPO-style pairs i-th best vs i-th worst with a score margin; returns `contracts.PreferencePair` plus diagnostics `frac_zero_variance_groups`, `frac_small_groups_dropped`, `n_pairs`, `mean_margin`, `n_groups_kept`); `dpo_loss_and_grad_coef`; `KLWeightGate` (from round 3: KL < 0.01 or relative weight change < 0.005 -> raise lr/rank once, then stop); `LegacyBinaryGRPO` (the previous recipe, kept as a control).
- `stop_monitor.py` (U2): `GapStopMonitor` (train / stop verifiers only; held-out never in the signature) plus `NeverStop` and `AlwaysStop` controls.
- `toy_policy.py`: tabular softmax-policy environment where the old binary recipe stalls (zero-variance groups) and the graded recipe learns; `hack_env.py` + `sim_u2.py`: planted hackable-proxy environments and the monitor's operating characteristics.

## 2. U3 control (unit tests, `test_preference_updater.py`)
Concentrated start policy (all mass on prompt-specific items that pass the binary threshold): expected >90% zero-variance groups, legacy gain ~0 and KL ~0; graded updater gain > 0.10 and KL > 0.01. Broad start: the legacy updater must learn (gain > 0.01), which shows the stall comes from the variance structure and not from a broken legacy code path. Both directions of the control can fail.

## 3. Pre-registration AMENDMENT A1 for U2 (committed BEFORE any simulation run; 2026-10-29)
**Monitor parameters (fixed):** q = 0.10 (top fraction by TRAIN score), patience = 3, tau = 0.5 (round-0 SD units; smoothed gap above its running minimum), tol = 0.05, warmup = 2, smooth = 2. Restore round = argmax of the stop-gain S_t.
**Environments (fixed):** `hack_env.py` kinds `hackable` (c_h = 5, c_s = 1), `benign` (c_h = 0, c_s = 0), `shared` (stop verifier shares the train exploit; the monitor is EXPECTED to fail there; reported as a limitation, no claim). ES: d = 10, n = 64, sigma = 0.3, lr = 0.5, 30 rounds, observation noise 0.3. Ground truth H = -||x - x*||^2 is used ONLY to score outcomes.
**Stage A (environment validity, DEV seeds 9000-9199, NO monitor evaluated):** valid iff (hackable) NeverStop retains < 0.7 of the peak held-out gain in >= 70% of runs and (benign) NeverStop median retained >= 0.90. If invalid, the environment parameters may be amended once (new commit, before stage B); no monitor result exists at that point.
**Stage B (monitor evaluation, TEST seeds 0-399 per kind):** outcomes on held-out truth only: retained fraction R = (H_restore - H_0)/(H_max - H_0); detection delay = stop round - argmax H; false-stop rate in `benign` = P(stopped and R < 0.9); missed-hack rate in `hackable` = P(R < 0.75).
**Primary contrast:** equal-weight mean of R over {hackable, benign}; GapStop minus NeverStop and GapStop minus AlwaysStop, paired by seed, 95% bootstrap CI of the mean over 400 runs. Unit of inference: the simulated run (these are simulations; they say nothing about real verifiers).
**Verdict vocabulary:** GO if both primary lower bounds > 0 AND benign false-stop rate <= 0.10 (Wilson upper bound reported) AND hackable missed-hack rate <= 0.20 AND median hackable delay in [-2, +4] rounds; NO-GO-detectable if either primary upper bound < 0; otherwise INCONCLUSIVE. Comparator without a pass criterion: Track E's `pmo_harness.StopMonitor` with inputs mapped to [0,1] via 0.5 + z/6.
**Controls that can fail and pass:** NeverStop must lose on `hackable` (validity criterion), AlwaysStop must lose on `benign`, and the monitor must beat both on the primary; the `shared` environment documents the failure mode.


### 3b. AMENDMENT A2 (declared 2026-10-29, before the dev-grid run; test seeds 0-399 NOT touched)
Stage A (A1) found two design problems, both visible only on DEV seeds / unit tests, no test-seed monitor result exists:
(i) environment validity FAILED for `hackable` (c_h = 5, T = 30): NeverStop retained < 0.7 of the peak in 27.5% of dev runs (needs >= 70%; median 0.72); `benign` passed (median 1.0);
(ii) two unit tests failed: the A1 per-round top-q statistic false-stopped a noisy plateau, and the planted Goodhart shape appeared in 7 of 20 hackable seeds (< 12).
Changes (declared now): (a) monitor statistic = best-so-far set by TRAIN score (k0 = round(q x first-batch size)), see `stop_monitor.py`; (b) the environment exploit strength and horizon are chosen from the grid c_h in {5, 5.5, 6, 7} x T in {30, 40} by the A1 validity criteria on DEV seeds 9000-9199 (smallest c_h, then smallest T that is valid); (c) monitor parameters are chosen on the same DEV seeds from the grid tau in {0.5, 1.0} x patience in {3, 4} x smooth in {2, 3} by: maximise the equal-weight mean retained fraction over {hackable, benign} subject to benign false-stop rate <= 0.10 and hackable missed-hack rate <= 0.30; ties -> smaller tau, patience, smooth. q = 0.10, tol = 0.05, warmup = 2 unchanged. The selected values are committed (A2-final) BEFORE stage B; stage B uses test seeds 0-399 only. Honest note: monitor parameters are therefore tuned on simulated dev environments; the stage-B comparison is on fresh seeds of the same environment family and says nothing about real verifiers.

### 3c. A2-final (selected on DEV seeds 9000-9199 by the rule declared in 3b; committed before stage B)
Stage-A' dev results (`results/stageA_dev_grid.json`): environment cell c_h = 5.0, T = 30 invalid (27.5% of NeverStop runs below 0.7); c_h = 5.0, T = 40 valid (100% below 0.7, median retained 0.554, benign median 0.9997) -> **chosen: c_h = 5.0, T = 40**. Monitor grid (benign false-stop / hackable missed-hack / mean retained): only (tau 1.0, patience 4, smooth 3) meets missed-hack <= 0.30 (0.285; false-stop 0.00; mean retained 0.896); the runner-up (tau 0.5, patience 4, smooth 3) has missed-hack 0.305. **Frozen: q = 0.10, tau = 1.0, patience = 4, tol = 0.05, warmup = 2, smooth = 3, T = 40.** Stage-B outcomes and the A1 primary/verdict rules are unchanged.
**Documented limitation (winner's curse).** The best-so-far statistic grows by selection alone when the train score carries noise, while the independent stop score does not; a plateau can therefore look like a widening gap. This is why the unit test uses a shared latent quality for both verifiers (an earlier version with a pure-noise train score false-stopped), and why tau = 1.0 was selected. The monitor assumes the train and stop verifiers measure related quantities.

## 4. Prior art (primary arXiv pages opened 2026-10-29 through the fetch tool, whose output is a model-generated extract: re-verify before external use)
- **Gao, Schulman & Hilton, arXiv 2210.10760, "Scaling Laws for Reward Model Overoptimization"**: measures the divergence between a proxy reward model and a gold reward model during optimisation (RL and best-of-n) and reports method-dependent functional forms; the abstract proposes no stopping monitor. Relevance: the empirical phenomenon U2 monitors.
- **Moskovitz et al., arXiv 2310.04373 (ICLR 2024), "Confronting Reward Model Overoptimization with Constrained RLHF"**: composite reward models, overoptimisation thresholds ("proxy points") and Lagrange-multiplier weighting, found by an adaptive gradient-free method within a single run; LLM alignment; not framed as early stopping.
- **EvalStop, arXiv 2606.04145 (June 2026), Zhang et al.**: stops RLHF jobs after k consecutive declines of a downstream evaluation score and keeps the best checkpoint; LLM fine-tuning platforms; no chemistry.
- **Gao et al., arXiv 2206.12411 (PMO)**: 25 algorithms, 23 tasks, 10K oracle calls; the abstract does not address held-out oracles or reward hacking (the generation-evaluation survey, `20261031_SURVEY_GENERATION_EVALUATION.md`, covers molecule-specific hacks).
- DPO, GRPO variants, rank/variance-filtered advantages: **not opened** by this workstream, so no novelty claim about them ([UNVERIFIED]).
**What is and is not new.** U2's mechanism (stop when an independent signal stops improving while the optimised signal keeps rising; restore the best checkpoint) is NOT new: EvalStop and the validation-signal tradition already do this for LLM RLHF. What this workstream adds is (i) the explicit three-way verifier split (train / stop / held-out) as a protocol for oracle-budgeted molecular optimisation, (ii) stated operating characteristics on planted environments (detection delay, false-stop and missed-hack rates), and (iii) the winner's-curse limitation of best-so-far statistics. Whether anything of this kind exists for molecular design is [UNVERIFIED] (not searched beyond the PMO abstract). U3 claims no algorithmic novelty: it is a diagnosis (binary reward + start policy consistent per prompt -> zero-variance groups) and a fix assembled from standard components, evaluated in our setting.

### 5.3 U3 LoRA/DPO smoke on ChemFM-1B (CPU torch, EC2)
**Smoke v1 and v2 produced no preference pairs because of a bug in the smoke script, not a property of the updater or of ChemFM.** The script constructed `GradedPreferenceUpdater(group_size=N_PER)`, so a group needed ALL of its samples to be valid; ChemFM's unconstrained validity at prefix 0.6 is 0.67-0.75 (v1: 16 samples/prompt; v2: 32 samples/prompt), so every group was dropped (frac_small_groups_dropped = 1.0), no DPO step ran and KL stayed 0. (An earlier edit of this note wrongly attributed v1 to `valid members < 16`; that was incorrect for the script as written and is corrected here.) The true design observation that remains: `group_size` counts VALID members, so with an unconstrained LM at validity ~0.7 the nominal group must be about group_size / validity; the rule automaton (valid by construction) removes this waste. v3 fixes the script (`GROUP_MIN_VALID = 16`, N_PER = 32).
**Smoke v3 result** (`results/smoke_v3.json`; ChemFM-1B pinned revision, LoRA r = 8 on q/v, CPU torch on a c5.9xlarge spot instance, 3 rounds x 4 prompts x 32 samples, 4 DPO steps per round, lr 1e-4, beta 0.1; the graded score is an arbitrary smooth physchem objective chosen only to create within-group variance): 12 DPO steps ran. Pre-stated sanity checks: step-0 loss = ln 2 (0.69315) PASS; all losses finite PASS; relative LoRA weight change > 0 after the first step PASS. All 4 groups were kept in every round (frac_small_groups_dropped = 0, frac_zero_variance_groups = 0), 8 pairs per round, mean pair margin 0.65-0.78. Loss fell within each round (0.693 -> 0.657, 0.685 -> 0.654, 0.676 -> 0.652).
**What the smoke does NOT show.** Mean sampled score did not improve (0.474 -> 0.490 -> 0.450; 12 steps at lr 1e-4 on re-sampled data is far too little to expect it, and no claim is made); the sample-based KL estimate is 0.0006-0.002 nats/token and the relative weight change reached 0.0031 after 12 steps, both below the gate thresholds (0.01 and 0.005), i.e. at round 3 `KLWeightGate` would have returned `raise_lr_rank_once`, the same regime as the earlier v4 DPO (relative change 0.001). This is a plumbing check (loss, KL, pairs behave), not evidence that the recipe improves a generator.
