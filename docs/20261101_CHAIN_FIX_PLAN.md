# Plan: make the defined workflow chains actually run

Date: 2026-11-01. Evidence: `20261101_WORKFLOW_CHAIN_AUDIT.md` (generated by `scripts/audit_workflow_chains.py`).

## Problem
No chain has a recorded run (sum of `usage_count` = 0). 17 of 69 chains contain a step that resolves to no executable workflow. The executor passes an upstream
artifact as `params[to_input]` (`workflow_chain._apply_connection_handoffs`); only 5 of 137 connections name a parameter the downstream workflow declares (85 do not,
47 undeterminable). A long chain is therefore expected to launch a doomed Batch job at step 2 or 3. The chain table lives in `backend/database/galaxy_ai_tools.db`,
which is git-ignored and shipped to dev by `sync_to_dev.sh`, so repairs must be a committed script plus a committed spec.

## Principles (CLAUDE.md)
Fix the root cause; no guessing mappings. A connection that cannot bind must fail loudly before launch, never inject an unused parameter. Review before any expensive run.
Chains are repaired explicitly from the downstream workflow's declared parameters, not by heuristics.

## Workstreams (independent; disjoint files)
| Id | Work | Files owned | Acceptance |
|---|---|---|---|
| W1 | Runtime strict binding. Before launching step N, check every connection into N: `to_input` must be a parameter the downstream workflow declares (main.nf `params.X` plus `nextflow_schema.json`). If not, the step is marked failed with a message naming the connection, the workflow and its declared parameters; no job is launched. Same check at submit time returns the problems with the response. | `backend/lib/galaxy/webapps/galaxy/api/workflow_chain.py` (new helper module `backend/lib/galaxy/chain/binding_check.py` + test) | Offline tests: matching name binds; non-matching name fails before launch with the stated message; connection-less chains unchanged; python3.9 compile; existing chain tests still pass |
| W2 | Repair spec and script. `backend/scripts/repair_workflow_chains.py` applies `backend/config/chain_repairs.json` to the DB idempotently (prints before/after, supports `--dry-run`, backs up the DB first). Priority chains: `andv_inhibitor_track_v1`, `drug_discovery_admet_gated_screening`, `bulk_rnaseq_de_analysis`, `rare_disease_multimodal_workup`, `bioc_bulk_rnaseq_de_v2`. For each: correct each `to_input` to a declared downstream parameter, and pin unresolved steps (`structure_prediction_docking` to the real docking workflow) by `workflow_id` or `nextflow_path`. Every change is justified in the spec by the downstream workflow's declared parameter. A chain that cannot be repaired without a new workflow is listed as such, not patched. | `backend/scripts/repair_workflow_chains.py`, `backend/config/chain_repairs.json`, test | After applying, `audit_workflow_chains.py` shows the priority chains with 0 mismatches and 0 unresolved steps; dry-run output reviewed; DB backup made; idempotent second run is a no-op |
| W3 | Linter and checklist. `scripts/lint_workflow_chains.py`: exits non-zero if a chain on the required-clean list (starts with the W2 five) has an unresolved step or a mismatching connection; prints the rest as a report. Add it to `docs/PRE_SYNC_CHECKLIST.md`. Add a unit test over a tiny fixture DB. | `scripts/lint_workflow_chains.py`, `scripts/test_lint_workflow_chains.py`, `docs/PRE_SYNC_CHECKLIST.md` | Passes on the repaired DB, fails on a deliberately broken fixture; documented in the checklist |
| W4 | Dev end-to-end run of one repaired chain. Needs the W1 backend change and the repaired DB on dev, i.e. a sync. Predicted outcome written first. Gated: waits for the user's go-ahead for the sync, because `sync_to_dev.sh` also tars the frontend working tree. | none (evidence in `docs/`) | Chain completes or fails with a diagnosed cause; step handoffs logged |

## Order and risks
W1, W2, W3 run in parallel now. W3 depends on W2 only for its required-clean list (it reads the list from a constant until W2 lands). W4 starts after all three are
committed and the user approves the sync. Risk: a repaired mapping may bind a file but the downstream workflow may still need extra parameters; W4 will show this. Risk:
nf-core pipelines declare parameters outside `main.nf`; the checker treats those as undeterminable and reports them, it does not pass them silently.

## Not in this plan
Capability steps in chains, the gate field, the planner (see `20261101_ORCHESTRATION_OVERVIEW_AND_UNIFICATION.md`), and the other 64 chains (reported by the linter, repaired later by the same spec).
