# Germline E2E Test Failure Analysis — 2026-03-24

**Tests**: `frontend/e2e/germline-complete-e2e.e2e.ts`
**Status**: 4 failed / 2 passed (GC-3, GC-4 pass reliably)
**Failing**: GC-1, GC-2, GC-5, GC-6

---

## Overview

The 4 failing tests probe the full conversational + execution loop for germline variant calling. They are not failing due to code bugs in the infrastructure — the Nextflow search, workflow card rendering, param wiring, and API endpoints are all functional (GC-3 and GC-4 verify these). The failures are rooted in **LLM behavioral non-determinism**: the AI assistant does not consistently follow the expected conversational logic.

---

## GC-1: Disambiguation → Germline Workflow → Execute

### What the test expects
1. Send an ambiguous query: *"I want to perform variant calling on whole genome sequencing data using BWA and GATK"*
2. AI should either ask germline vs somatic clarification **or** generate a workflow.
3. User sends Turn 2: *"This is germline variant calling for inherited disease — single patient, no tumor sample"*
4. AI must produce a **germline** response (not somatic-only).
5. A Nextflow workflow card should appear.
6. Execute API should accept the run.

### What actually happens (observed in screenshots)

**Turn 1** (`gc1_02_after_first_query.png`): The AI skips clarification entirely and immediately generates a "Whole Genome Sequencing Variant Calling Workflow" with BWA-MEM2 as Step 1 — no question asked. The Step 1 assertion is lenient enough (`generatedWorkflow=true` suffices) so Step 1 passes.

**Turn 2** (`gc1_03_after_germline_answer.png`): The AI returns a long **text-only Markdown response** listing GATK HaplotypeCaller steps, BQSR, Required Inputs, Expected Outputs — but **no Nextflow workflow card** is emitted. The bottom of the response says *"Please provide your FASTQ file paths/accessions and reference genome to fully parameterize and execute the workflow!"* — it is asking for data again instead of generating a runnable card.

### Why it fails
- The test code at line 445–453 does a soft return if `cardFound=false` (no hard `expect`). The test should technically pass as long as `isGermlineResponse=true`.
- Failure is instead at **Step 1 on certain runs** when the LLM returns a "Workflow Generation Failed — Let's Recover!" error message that none of the five classifiers (`askedClarification | generatedWorkflow | panelVisible | askedForDataset | failedWithRecovery`) detect, causing the assertion at line 372 to fail.
- The `failedWithRecovery` classifier prompt is too narrow — it misses error UI generated by the frontend (`ChatMessage` recovery template) as opposed to AI-authored text.

### Root cause (system behavior)
- The AI does not ask for germline/somatic disambiguation for an ambiguous query when it finds a workflow match, because the `workflowAmbiguity` classifier in `galaxy-assistant.ts` fires only for specific `variant_type`/`rnaseq_type`/`scrna_type` fork points. A query that already names tools (BWA + GATK) is treated as unambiguous by the system prompt.
- On Turn 2, the AI enters a "describe workflow" mode (Markdown text) rather than re-invoking the workflow generation tool, because the system prompt's "dataset-first" rule triggers again on the second message (no dataset was ever provided).

### Improvement suggestions

**System-level (highest impact)**:
1. **Teach the AI to recognise that Turn 2 is a clarification response, not a new query**. Add a system prompt rule: *"If a user's previous message generated a workflow and they are now providing a type qualifier (germline/somatic/bulk/single-cell), immediately regenerate the workflow with the qualifier applied — do not re-ask for data."*
2. **Suppress the dataset-first gate on Turn 2+** when the conversation already has a workflow in progress. The current rule fires on every message. It should only fire on the first workflow-generation request per session.

**Test-level (medium impact)**:
3. The `failedWithRecovery` classifier at line 348–354 should also match the frontend-rendered error template text (look for "Workflow Generation Failed" or "data-loading error" in the DOM, not just in the AI text).
4. Step 1 assertion should be a `console.warn` + `test.skip()` for the "generation failed" path rather than a hard `expect`. A backend initialization error is infrastructure, not a routing bug.

## GC-2: Direct Mock Germline Execution → Terminal State → Outputs

### What the test expects
1. Send explicit germline+SRR query: *"Run germline variant calling using GATK HaplotypeCaller on SRR1518169 (NA12878 paired-end WGS from NCBI SRA, hg38 reference). I want to identify inherited SNPs and indels for rare disease diagnosis."*
2. AI must NOT ask a redundant germline/somatic clarification.
3. AI must generate a germline workflow card.
4. Click "Run Workflow" button.
5. Poll to a terminal state (`completed` | `failed` | `error` | `cancelled`).
6. `GET /api/workflows/runs/:id/output_files` must return HTTP 200.
7. `GET /api/workflows/runs/:id/download_commands` must return HTTP 200.

### What actually happens

The workflow card is rendered correctly (`gc2_02_workflow_card.png`): "Run germline variant calling using GATK" shows HaplotypeCaller, BQSR, GenotypeGVCFs, SnpEff steps. The "Run Workflow" button is visible and enabled.

However, the execution panel (before our `hasUnfilledRequired` fix was first applied this session) was showing:
- **Input data: warning — 5 required input(s) are missing.**
- **Required parameters: warning — 4 optional/suggested parameter(s)** (should be HARD MISSING)

This is now corrected — the `prereq-normalizer.ts` `!= null` fix and `hasUnfilledRequired` block now properly identify `reads`, `reference`, `known_sites`, `dbsnp_vcf` as required. **After our fix**, the button should be disabled. The test has a recovery path: if the button is disabled, it looks for `button-prereq-recovery`, clicks it, and tries again with "demo inputs".

### Why it fails

**Scenario A — Before the `hasUnfilledRequired` fix**: The button was enabled despite empty required params. The workflow executed but with blank params, causing a Nextflow error immediately. The run entered `failed` state quickly — which the test accepts (`expect(["completed", "failed",...]).toContain(finalStatus)`). The failure is then at the **output_files or download_commands API assertion** after terminal state, or at a timeout if Nextflow never transitions to terminal.

**Scenario B — After the `hasUnfilledRequired` fix**: The button is disabled. The test falls back to `button-prereq-recovery`. The recovery button appears only when `isPrereqBlocked=true && prereqChecklist?.overrideAllowed !== true`. If the recovery button is visible, the test clicks it and sends a message to the AI asking for demo inputs. This conversational round-trip (recovery AI response + new workflow card with `allowPrereqRecovery=true`) introduces another LLM call that may not complete correctly.

**Scenario C — Workflow execution timeout**: The Nextflow job is dispatched to AWS Batch. With no real input data, it may hang in `PENDING` state indefinitely (no Spot capacity, ECS throttling). The test's inner `pollToTerminal` has a 9-minute timeout but the run may never reach terminal.

### Root cause
- The core issue is that **the E2E test requires real workflow execution** without providing real data. Mock mode (`?mock=true`) exists in the Nextflow executor but is not being activated by this test path. The test uses the full real backend.
- The `dataset-first` system prompt creates a tension: the test provides an SRR accession, but the prereq validator does not map SRR accessions to `reads` parameter → the `reads` field stays empty → button disabled.

### Improvement suggestions

**System-level (highest impact)**:
1. **Map SRR accessions to input params in the prereq validator.** When a query contains an SRR/ERR/DRR accession (detectable via regex `[SED]RR\d{6,}`), the system should auto-set `reads = SRR1518169` in the generated params (or mark `reads` as "provided via SRA fetch step"). This would allow the Run button to be enabled for SRA-based workflows.
2. **Add `mock_mode: true` to the default test params** emitted by the AI for mock/demo queries. The Nextflow executor respects `params.mock_mode` and short-circuits to synthetic output. The test query contains "mock" or "demo" keywords that the AI recognises but does not pass through to params.

**Test-level (medium impact)**:
3. Before clicking Run, the test should explicitly set a value for each required param via the UI (e.g., type `SRR1518169` into the `reads` field). This removes the dependency on the AI correctly pre-filling required params.
4. The `pollToTerminal` timeout (9 min) should short-circuit if the run has been `PENDING` with no state change for >2 minutes — AWS Batch jobs that never start should be treated as `failed` rather than hanging.

## GC-5: Inline Data Provision — SRR Accession in Query

### What the test expects
1. Send query with inline SRR accession: *"I want to run germline variant calling with GATK HaplotypeCaller on my WGS sample. The data is publicly available at NCBI SRA under accession SRR1518169 (NA12878 paired-end, hg38 reference). Please generate the workflow."*
2. AI must **NOT** ask for data again (it was provided).
3. AI must mention `SRR1518169` **OR** generate a germline workflow.

### What actually happens

The `dataset-first` system prompt rule instructs the AI: *"Before generating a workflow, ask for data info (file path, S3 URI, accession)"*. The LLM does not reliably detect that an SRR accession in the query body constitutes "data already provided" — it sometimes treats the accession as a mention rather than as actionable data, and re-asks for a file path or S3 URI.

This is non-deterministic: sometimes the AI correctly proceeds to generate the workflow using the accession; other times it says something like *"Great, I have your SRR accession. Could you also confirm the S3 URI or FASTQ path for the raw reads?"*

### Why it fails
- **The `dataset-first` system prompt rule does not define what counts as "data provided"**. It is phrased as a gate to ask for data, not as recognition logic to detect when data is present.
- SRR accessions are not FASTQ paths or S3 URIs. The AI correctly notes that SRA requires a fetch step — so it asks for the "raw reads path" even when the SRR is provided, because it's uncertain whether the fetch will happen automatically.

### Root cause
The system prompt in `galaxy-assistant.ts` has:
> *"The AI must ask for data info (file path, S3 URI, accession) before generating a workflow. Exception: demo/test/mock requests."*

The exception does not cover "user provided an SRA accession". The AI interprets the rule literally: SRR ≠ file path/S3 URI → ask for one.

### Improvement suggestions

**System-level (highest impact)**:
1. **Extend the dataset-first exception list**: *"Exception: demo/test/mock requests, OR queries that already contain an SRA accession (SRR/ERR/DRR prefix), OR queries that include a file path or S3 URI."* Add concrete regex examples so the LLM recognises them.
2. **Add a system prompt instruction**: *"If the user's message already contains an SRR/ERR/DRR accession number, treat this as the data source. Proceed directly to workflow generation using that accession as the `reads` parameter. Do NOT ask for a file path."*

**Test-level (low impact)**:
3. The assertion `mentionedAccession || generatedWorkflow` at line 1081 is already lenient. The test fails because NEITHER is true — the AI asks for data instead of mentioning the accession meaningfully. The fix must be on the system side; the test assertion is already appropriate.

## GC-6: Two-Turn Data Provision — Ask Then Provide

### What the test expects
1. **Turn 1**: Send query WITHOUT data: *"I want to run germline variant calling with GATK HaplotypeCaller for rare disease diagnosis"*
2. AI must do ONE of: (a) ask for data, OR (b) generate a workflow with MISSING input markers.
3. **Turn 2**: Provide SRR: *"My data is available from NCBI SRA, accession SRR1518169. It's a paired-end WGS sample from NA12878, aligned to hg38."*
4. AI must generate or update a germline workflow using the accession.

### What actually happens

**Turn 1**: The AI produces a **general explanatory response** — neither asking for data nor generating a workflow. Example observed response (inferred from `askedForData=false generatedWorkflow=false`):
> *"Germline variant calling with GATK HaplotypeCaller is a well-established pipeline for identifying inherited SNPs and indels. Key steps include BWA alignment, GATK BaseRecalibration, and HaplotypeCaller in GVCF mode. For rare disease diagnosis, gVCF mode is preferred as it supports future joint genotyping..."*

The AI "explains" the workflow instead of taking action. The `askedForData=false` (no question was asked) and `generatedWorkflow=false` (no workflow card emitted) both return false, causing the assertion at line 1136 to fail immediately before Turn 2 even runs.

### Why it fails

The system prompt has two competing rules:
1. *"Ask for data before generating a workflow"* — should trigger here (no data provided).
2. *"Be helpful and informative"* — the LLM defaults to explaining instead of asking.

When the query is **conceptual** (no file, no accession, no mention of "I have data") and **specific enough** that the LLM can give a full answer, it enters explanation mode rather than asking a question or generating a card.

The LLM's instruction-following is inconsistent for open-ended queries of this type. In some runs it asks for data; in others it explains; in rare cases it generates a workflow immediately.

### Root cause
The `dataset-first` instruction is a soft guideline, not a hard gate. The LLM treats it as "prefer to ask" but not "always ask". When the intent is clear enough to answer without data (a tutorial-style response), the LLM takes the path of least resistance: explanation.

There is also no **conversation-state tracking** on the frontend side — the AI does not know that the *intent has been established* and what it needs to do is *gather inputs*, not explain. This is a stateless limitation.

### Improvement suggestions

**System-level (highest impact)**:
1. **Make the data-first gate unconditional and explicit**: Change the system prompt from *"ask for data info before generating"* to *"NEVER generate a workflow or provide step-by-step execution instructions without first collecting the user's data source (file path, S3 URI, or SRA accession). This is non-negotiable even for well-understood workflows."*
2. **Add a "pending input" state to the system**: When `askedForData=true` but no workflow was generated, persist a `pendingWorkflowRequest` in the session. On the next user message, check if it satisfies the pending request before doing anything else.
3. **Teach the AI to ask specifically, not generally**: Rather than a generic "please provide your data", prompt it to ask for the SPECIFIC params that are missing: *"To run this GATK germline pipeline I need: (1) raw reads (FASTQ path, S3 URI, or SRA accession like SRR123456), (2) reference genome (hg38/GRCh38 is default). Which do you have?"*

**Test-level (medium impact)**:
4. The Turn 1 assertion `askedForData || generatedWorkflow` is correct. However, the test could be more resilient by **also accepting** a third condition: `isExplainingTheWorkflow=true` (classifier: "did the AI explain the workflow steps without generating a runnable card?"). If the AI is in explanation mode, the test should log a warning rather than hard-fail — the interesting assertion is Turn 2.
5. An alternative: pre-seed the conversation with a system message that establishes data context before the test query, eliminating Turn 1 entirely and focusing GC-6 purely on Turn 2 data provision.
