Foundations & the cold start

BioMate · Function-module spec 00 of 09Status: for reviewPrototype: BioMate Data-Centric Prototype.html

BioMate can do a great deal, and almost none of it is legible from a blank chat box. This spec set fixes that by naming four things a scientist can do — search for evidence, analyse data, work with models, and design candidates — and specifying every view and element through which they are offered, entered, watched and audited. This document covers what the four share: the lane model, the cold-start view, the composer, the evidence taxonomy, and the copy rules that keep the surface honest.

0.2Why four modules, and not two or nine

The old surface offered four peers — Ask, Compute, Skills & experts, Workflows. Two problems. One: Compute and Workflows are the same user intent ("do something with my data"); the difference between them is how much rigour the question deserves, which is a system judgement, not a menu choice. Two: Skills & experts is not a thing you do at all — it modifies how any of the others reason. Presenting it as a fourth card taught users to look for it in the wrong place.

Collapsing Compute and Workflows leaves three distinct scientific jobs. A fourth was then earned, not invented: designing new molecules is neither analysing data you already have nor training a predictor, and for a lead-discovery programme it is the whole job. The test for a module is this — can a scientist say the sentence, and is the sentence a different job?

ModuleThe user's sentenceWhat comes backLane
Search & evidence"What is known about…"A cited answer. Nothing runs on your data.Instant
Design & generate"Propose and rank new molecules."Candidates with predictions, trade-offs and a shortlist.Instant → Cloud
Data analysis"Do this to my data."A number, a figure, or a gated run with a report.Instant → Cloud
Models"Learn from my data."A versioned model object with held-out evidence.Cloud
Naming rule

Modules are named for the user's goal, never for the implementation. "Deep learning" was rejected for module three: it names a technique, excludes the classical models scientists also want, and forces a user to know which family their problem belongs to before they can start. Models also matches the model objects already in the product.

0.3The two lanes

Every request resolves to one of two execution lanes. The lane is a promise about time and rigour, and it is always stated back to the user before work begins.

LaneTimeWhere it runsWhat it guarantees
InstantSecondsIn the conversationCitations on every claim, or code shown for every number. Sandbox is network-isolated.
CloudMinutes to hoursA run object in the projectQuality gates, a resolved-parameter record per step, an audit-ready report.

Lane arbitration

BioMate picks the lane from the goal and the data, and says which it picked. Three rules govern the pick:

  1. Rigour follows consequence. A look at a distribution is Instant. Anything a figure, a filing or a decision will rest on goes Cloud, because only Cloud produces the parameter record and the gates.
  2. Scale forces the lane. Work that cannot finish in the conversation is Cloud regardless of intent.
  3. The system chooses by default. The stated lane explains the trade-off. A user who needs to change it can use Advanced → switch lane, where the time and rigour consequence is shown.
Why say the lane out loud

The failure we are designing against is a scientist pasting a table, getting a plausible number in four seconds, and putting it in a manuscript. Naming the lane makes the trade visible at the moment of asking: this was the fast answer; the gated one takes eleven minutes.

0.4.3 The thin launcher

Returning users do not need the dashboard. .thinlaunch is the same view reduced to the composer plus four .modpill buttons and an expand link. Clicking a pill expands the dashboard with that module already open. The state persists for the session only — never across accounts, and never silently for a first-time user.

0.4.4 Project scope

A chat started inside a project shows one extra line: In Fibrosis Target ID · its files and instructions are in context. Nothing else changes — the modules are identical. What differs is what the composer can resolve without asking: files, project instructions, the figure spec, prior runs. See Spec 06 §6.4 and Spec 07 §7.4.

0.5The intent router new

The composer is not a search box, and this distinction carries the whole design. A search box implies an index of things we sell, and invites the question "so what else have you got?" — which we answer badly, because the honest answer is a list nobody should be reading. The router instead restates the goal in system terms and offers to start.

Router returnsNever returns
A lane — Instant · search, Cloud · workflow, Cloud · models.A ranked list of workflow names.
A domain — Drug discovery, Transcriptomics, Patents, Models & training.A count of how many things matched.
A Start button that seeds a normalised version of the goal.A "no results found" empty state.

Behaviour

  • Matching is on intent words, not product names: herg|admet|smiles|liabilit → Cloud · workflow / Drug discovery; train|fine-tune|reinforce → Cloud · models; patent|freedom to operate|claim → Instant · search / Patents.
  • No match, no box. The user keeps typing and sends; the conversation resolves the ambiguity in words, which it is better at than a router.
  • Start seeds the composer with a canonical phrasing of the goal — it never launches a run. Every run is confirmed on the run surface. shipped
  • The router is covered by a self-test. Every example sentence printed on a module card must route to that module, and every route's own seed must match its own rule. The cards make a promise about what the router understands; the test is what stops the promise drifting. new
Copy rule

No self-justification in the UI. Earlier drafts wrote "not a search box — it routes your intent, it does not return a list of our workflows" under the input. That is a designer arguing with the user inside the product. The label is Describe the goal and the behaviour explains itself.

0.6Skills & experts — a modifier, not a module

Expert reasoning packs — pharmacology, regulatory, biostatistics, structural biology — change how an answer is reasoned, not what BioMate can do. They therefore live in the composer as toggles, not in the module grid. Rules:

  • Active packs are visible wherever a request is made, and are recorded on the answer and in the run's audit trail.
  • A pack never changes the lane, the parameters, or the data — only the reading and the framing. If a pack would change a parameter, that is a project instruction, and belongs in Spec 07 §7.4.
  • Packs are toggled, never browsed as a directory. The set is small and editorial. open whether users can author their own.

0.7Evidence classes new

Every artifact a run produces has an evidence class — the kind of evidence it is — and the class, not a guess at the moment of rendering, selects the viewer. This is what lets a step's output be looked at properly instead of downloaded blindly.

Resolution rule new

The class is resolved from the output itself — extension first, content sniff for anything unknown or ambiguous — consistently, wherever it is rendered. It is deliberately not specified as a backend tag: output objects are not uniform across pipeline builders (some carry name, some filename, some no extension at all), so a spec that assumed a reliable upstream tag would be assuming a contract that does not hold. One resolver, used by every surface, so the same artifact never renders as two different classes.

The UI contract is unchanged by that: every output has a class, and every class has a viewer. An output whose class cannot be resolved is shown as procedural with its raw bytes — never hidden, and never given a viewer that misrepresents it.

ClassWhat it isViewerExamples
PerceptualSomething you look at.Image stage with fit / 100% / 200% / full.Micrograph, density map, PCA, volcano.
SymbolicSomething you read.Record browser, jump by identifier.Sequence, annotation, normalised design table, report sections.
QuantitativeSomething you measure.Table with sort/filter plus column stats.Counts matrix, DE results, QC metrics.
ProceduralSomething that happened.Console with follow-tail.Nextflow log, R session, executor trace.
Integrity rule

A rendered view is derived from the artifact's own bytes. The table, the column stats and the raw view of one output are three renderings of one string, so they cannot disagree. Summaries are written from the artifact, and every number in a summary links to the output it is findable in (Spec 08 §8.6).

0.7.1 Domain viewers new

The four classes say which kind of viewer to open. Some outputs need a viewer specific to their science, and a generic viewer for them is a failure disguised as a rendering. These are instances of the classes, not exceptions to them.

OutputClassViewerWhy generic is not enough
Predicted structurePerceptual + quantitative3D view, plus a per-residue confidence chart linked to it, plus a pairwise-error heatmap.A structure picture alone invites a claim its low-confidence loops cannot support.
Per-base sequence scoresQuantitativeScore tracks over the locus, with flagged intervals as the actionable output.A 3,500-row table of per-base scores is unreadable; the interval is the finding.
Screening resultsSymbolic + quantitativeRanked hit table, and a 2D depiction grid rendered from the structures.A chemist reads structures, not identifier strings.

All three are specified in full where they are produced: structure and sequence viewers in Spec 03 §3.8, the hit grid in Spec 05 §5.5.

0.8Navigation copy new

Anchor-text rule

A nav item carries a label and nothing else. What a surface holds is said on that surface, in a line of anchor text under its title, where there is room to be accurate. Subtitles in a rail are the worst place to explain anything: 190px forces a truncation that is always either incomplete or wrong, and five of them turn a rail into a paragraph nobody reads.

Workspace connections used to be a primary rail item. That made setup look like a scientific job. Connections now live under Settings & workspace; the surface can explain data sources, models, skills and MCP servers without competing with the four research modules. Workflows still needs anchor text because it also imports validated pipelines.

SurfaceRailAnchor text on the surface
WorkflowsWorkflowsEvery run this account has started, and where new pipelines come in — one record per run, project chips as a filter, import available to every project.
Workspace connectionsSettings & workspaceEverything the workspace is attached to but does not own: data sources, models, skills, MCP servers.
ModelsModelsEvery model in the account and where each is used; training belongs to the project holding the data.

0.9Workspace connections: four sections, one settings surface new

Data sources, models, skills, experts and MCP servers are five different things. They belong in one settings surface because the question a user brings is always the same — what is this workspace attached to, and is it working? They are four sections rather than five because skills and experts are browsed together; see below.

0.9.1 We do not classify add-ons

This section went through two wrong answers before the right one, and both are worth recording because the pull toward each is strong.

  1. A lying label. Six reasoning packs sat under a tab called Skills, which told a user the platform could do six things when it could do none of them.
  2. An imposed taxonomy. The fix for that was to sort add-ons into two kinds — "does work" and "changes the reading" — and mark every row. But two buckets do not survive contact with real add-ons: a section-drafting skill is partly a reading, a reasoning pack can carry a procedure, and a user's own add-on frequently does both. Widening the taxonomy only defers the problem; there is no set of buckets that ends the argument. Classifying is not our job, and a category the user has to pick is a question we invented.
Declared facts, not categories

An add-on states what it needs, what it produces, and where it runs. Those are facts, they are verifiable, and every consequence follows from them without a taxonomy:

  • Produces an artifact → it runs as a step, with inputs, outputs and provenance, so what it made traces back to the run whose numbers it used.
  • Produces none → it is recorded on the answer as an active reading.
  • Residency says where it executes, so whether your data passes through it is answered on the row (prompt only means it cannot).
  • Nothing here may change a parameter — that is a project instruction (Spec 06 §6.5). This is the one hard rule, and it applies to every add-on regardless of what it is.

So the surface shows one list, sorted by nothing, each row reading "produces a .docx section · on-prem · built-in". The user names and describes their own add-on; we hold them to the declaration.

0.9.2 Scope: connected once, switched on per project

A skill or expert has three scopes, and they are the ordinary ones:

ScopeWhereMeans
AccountSettings & workspaceConnected. Available to the whole workspace. Connecting it does not switch it on anywhere.
ProjectThe project's Instructions pageOn here. A switch per item, so a project runs with the set that suits it — a chemistry project has different ones on than a clinical one.
RequestThe composerOn for this question. The popover is headed On in <project>, lists the account library with the project’s choices checked and badged project, and a change is marked changed on the chip — so a deviation reads as a deviation and the project default is untouched.
One list, one state

All three scopes read the same account library and the same per-project selection. The composer does not keep its own list of packs: a set of names hardcoded in the input box is how a project's stated configuration ends up contradicted by the surface that enforces it. The selector writes the state; the composer reads it.

Show the whole library, not just what is on

The project selector lists every connected skill and expert, with the unselected ones off, and says "none on yet" when nothing is. Rendering only the project's existing choices hides the affordance precisely where it is needed — a project that has chosen nothing would have no way to choose anything (the discoverability rule, Spec 03 §3.4.1).

Why the switch belongs on the Instructions page

Because it is an instruction — "in this project, read results for regulatory risk" — and it belongs with the other standing decisions rather than in a fourth place. An earlier draft tried to express this in prose instead, asking the user to write the sentence and BioMate to interpret it. That is worse in both directions: vaguer for the user and unverifiable for us. A choice from a known set is a switch, not a sentence.

The one rule that still holds

Switching an add-on on cannot change a parameter. Only a written instruction can do that, and the value then arrives on the run badged from project instructions (Spec 07 §7.4). So the page has two halves for a reason: sentences that change what runs, and switches that choose from what is connected.

0.9.3 Local is not a fifth kind new

Most of a pharma estate is local: data on a share or an HPC scratch path, a Postgres instance behind the firewall, self-hosted model weights. The wrong response is a "Local" category beside the other four — it would split every kind in two and answer a question nobody asks. A directory is a data source; your own weights are a model.

Residency rule

Locality is a property of a connector, not a kind of connector, and it is shown on every row, with no exceptions: cloud data leaves the estate · on-prem stays inside your network · mounted read in place, never copied · this machine never leaves the host · prompt only instruction text that moves no data. Residency is the dimension worth surfacing because it is the one users are accountable for.

No blank residency

A row with no marker is worse than a wrong one, and worst within a tab: if "write an IND section" is marked on-prem and "fit dose–response curves" is marked nothing, a user cannot tell whether fitting their curves sends data anywhere — the precise question the surface says it answers. Hence the fifth value: a reasoning pack moves no data, and says so, rather than saying nothing. A skill's residency is where it executes; a built-in skill runs on the same compute as a workflow step.

Residency is also functional, not decorative: data marked restricted routes only to models that stay inside the network, and the run records which one answered.

Adding a connector

Every kind can be added, not only the local ones — a data source (directory or database), a model, a skill, an expert, an MCP server. An add flow that covered three of five kinds implied the other two were fixed by us, which is false and is the kind of gap a user finds by looking for it.

KindMode
Skill or expertYou describe it; we do not sort it. Declare what it needs and what it produces, and the consequences follow — an artifact means it runs as a step with provenance, none means it is recorded on the answer. Scope it to a project or the account.
MCP serverURL, auth, and a capability review: its tools are listed before it is attached, and every capability it contributes is marked with the server it came from.

Adding something local

Nothing is attached until the user has seen what was found. A directory scan reports the file types and counts it detected, and what each will become, before it creates a single dataset object. Attaching 40,000 files and then explaining them is not a connector; it is a mess with provenance.

0.10.2 Colour does structural work in tables

A table of one flat tint makes the reader track rows by eye alone. Every row family — data sources, skills, ranked hits, evidence, versions, trajectory, wet-lab returns, the dataset preview — now carries:

  • A tinted uppercase header band, so the header reads as a header without a rule.
  • Zebra banding, so a wide row is followable across.
  • A hover state, and a left accent rail on the first row of a group.
  • Tabular numerals, so numeric columns align.
  • Flagged cells in amber with an outline — the visible evidence behind an amber verdict (Spec 04 §4.5.2).
Implementation note

Semantic row tints were first written as a :has() selector list across every row family; that stalled style invalidation badly enough to hang the page. Tints are applied by class from the component instead. Worth recording because the selector reads harmlessly.

0.11Every view resizes and hides new

Three panes — the sidebar, the project file list, the right panel — are drag-resizable from a 6px grip and collapsible from their own header. One component drags one CSS custom property; double-clicking a grip resets that pane.

0.13Verification is one pattern new

The product checks things in five different places. They are one concept with one reading: something is measured, against a threshold, producing a verdict. A scientist learns that shape once and can then read any check in the product. What differs is only who measures and what a failure stops.

CheckMeasured byA failure stopsSpecified in
Workflow quality gateA measurement on your data.The run, at that phase.Spec 07 §7.5
Model evaluation gateHeld-out performance against a floor.Registration — the model cannot be called.Spec 03 §3.3
Safety gateA predicted liability.A proposal, which stays visible with its reason.Spec 05 §5.4
Chemistry validity gateStructural correctness and accessibility.A generated structure, counted and characterised.Spec 05 §5.2
Human approvalA person.The run, until answered.Spec 07 §7.6
Verification rule

A human approval is a gate whose measurement is a person — that is the only difference, and it is why it uses the same measured / threshold / verdict layout as a QC gate rather than a bespoke dialog. Trust is the brand, so the vocabulary of trust may not fragment into five dialects.

0.14Roles and permissions new

BioMate is multi-tenant, so an action a user cannot take must be legible rather than absent. Four roles, and one rule about how they show up.

RoleCan
ViewerRead a project, its files, its runs and its reports. Run a workflow.
ContributorAdd files, edit parameters, start runs.
ReviewerOverride a quality gate; answer an approval delegated to a reviewer.
OwnerRegister a model, promote a file to the account, approve spend above the project threshold.
Disabled, never hidden

A control the current user may not use is shown disabled with the role it requires. Hiding it makes the product feel broken and makes a permission problem indistinguishable from a missing feature; naming the role makes it answerable — the user knows who to ask.

The gate-override and registration permissions are the load-bearing ones: they are exactly the actions that let a person overrule the evidence rules, so they are the actions that carry a name in the audit trail.

0.15Copy rules for the whole surface

  1. No inventory. No counts of workflows, models or experts; no browsable catalog of names. Categories and example shapes only — and this applies to the integrated pre-trained models too, which are presented by what they achieve rather than as a package list.
  2. No self-explanation. The UI does not argue for its own design decisions in body copy.
  3. Name the lane, name the cost. Time and rigour are stated before work starts, not after.
  4. Skipping is neutral. Language and colour for a skipped phase are the language of a choice.
  5. Every number is traceable. If a number appears in a summary or a report, it is a link to its source output.
  6. Say what ran, not what was requested. Parameters are shown as resolved, with their origin — default, inherited, detected, override — and a reason for anything that is not a default.
