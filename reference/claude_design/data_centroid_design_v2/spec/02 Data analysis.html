Data analysis

BioMate · Function-module spec 02Status: for reviewLane: Instant → Cloud

One module for everything done to the user's own data, with two gears: ad-hoc compute in seconds, and validated workflows in minutes to hours. Merging what used to be two peer entries is the central claim of this spec: the intent is identical — "do this to my data" — and the choice between gears is a judgement about how much rigour the question deserves, which the system is better placed to make than a user reading a menu.

Why one module

A user who wants a median does not think "I need the ad-hoc compute product". They think "look at my data". Two entries forced that irrelevant decision at the front door, and users chose wrong in both directions — casual questions into 40-minute pipelines, and manuscript figures out of unversioned sandbox code.

2.2Gear arbitration

BioMate picks, states the pick, and lets the user overturn it. The pick is a chip in the composer before anything runs.

  1. Consequence. Words like figure, manuscript, submission, report — or a project whose output requirement names a template — push to workflow.
  2. Named method. A request naming an established method (DESeq2, docking, variant calling) is a workflow, because the method has a validated implementation with gates.
  3. Scale. Work that cannot finish in the conversation is a workflow regardless of intent.
  4. Everything else is compute. Reshaping, summarising, correlating, plotting — the default gear, because it is the cheap one and the reversible one.
Escalation mid-thread

An ad-hoc result can be promoted: Redo this as a validated run. The compute code becomes the starting configuration, the run appears in the project, and the two results sit side by side so the user can see whether rigour changed the answer. This is the single most important path in the module, because it is how casual exploration becomes publishable work without being retyped.

2.4Views — validated workflows

The workflow gear is entered three ways: from the cold-start card, from the router, or by escalating a compute result. All three land on the same place — the workflow panel, on its Workflow settings section, with nothing yet run. The panel itself is Spec 07; this section covers only how the module presents choices before the panel. Skipping, gates and per-step parameters are specified there and in Spec 08.

2.4.1 Domains and shapes

Inside the opened module card, the Validated workflows track shows six domain chips: Genomics, Transcriptomics, Drug discovery, Structural biology, Clinical, Proteomics. Selecting one replaces the examples with that domain's shapes.

Inventory rule

A shape is not a workflow name. It is an achievement, and the pipeline, its version and its parameters resolve inside the session. Three shapes per domain, chosen editorially — enough to show the range, not enough to become a catalog. No counts anywhere: never "12 workflows available".

2.5Skipping phases new

Not every run needs every phase. A user re-analysing a dataset that already passed QC should not pay for QC again. Skipping is therefore a first-class configuration choice, not an error path.

  • Before the run: a Phases to run list of switches, with a live count — "18 of 22 steps".
  • During the run: a pending phase can still be skipped from its own card. A running or completed phase cannot.
  • A skipped phase is dashed and struck through, tagged SKIPPED in neutral grey — never red.
  • Downstream phases that depended on it show a gated row: "Phase B was skipped — this phase reads that phase's cached output instead of a fresh one."
  • The report's QC audit records the skip, so a reader of the report knows what was not checked.

2.5.1 Not everything is skippable new

Declared-skip rule

A skip is a capability the workflow declares, not a universal affordance the UI grants. A toggle appears only where the pipeline exposes a skip parameter for that phase and the dependency graph survives its removal. Offering a skip that the backend cannot honour, or that would orphan a downstream input, is worse than offering none — it produces a run that fails deep in phase C for a reason the user chose two screens earlier.

Three states, therefore, not two:

StateAppearanceCopy
SkippableAn active switch, with the declared parameter shown in mono beneath it — --skip-qc."Downstream steps read the cached output of the previous run."
Load-bearingThe switch is disabled, not absent, and the row carries a neutral chip."Can't skip · B, C depend on it" — plus the reason: "Phase B and C read A's alignments directly. The workflow declares no skip parameter for it."
Skippable but consequentialAn active switch with a plain-language warning."D would have nothing to work on" — the user may still do it; they are told what it costs.

The distinction is derived from two sources that must agree: the workflow's declared skip parameters, and a validation of the dependency graph with that phase removed. Where they disagree, the phase is treated as load-bearing — the conservative direction, because a false "you may skip this" is a broken run and a false "you may not" is only an inconvenience.
