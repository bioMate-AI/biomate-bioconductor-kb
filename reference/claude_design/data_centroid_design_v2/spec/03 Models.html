Models

BioMate · Function-module spec 03Status: for reviewLane: Cloud · hours

The backend is built: training, reinforcement fine-tuning, adapters, a registry, inference at scale. None of it is legible in the product. This spec is therefore almost entirely a presentation and integration problem — how a trained model becomes an object a scientist can see, judge, trust and use, and how it enters the surfaces they already work in rather than becoming a machine-learning annex nobody visits.

3.1The design problem

Three ways a models feature normally fails, all of which this spec is written against:

FailureWhat it looks likeOur answer
The ML annexA separate section with experiment tables and loss curves that only an ML engineer opens.Models appear inside the surfaces where they are used — a gate, a score column, a proposal — and the module is where you go to interrogate them, not to find them.
The leaderboardA ranked list of runs by metric, which teaches users to chase a number.A model passes or fails a held-out gate with a floor. There is no ranking, and a model that clears the floor is not "better" than one that clears it by more.
The unaccountable predictionA number appears in a table with no provenance.A prediction always carries the model name, the version and a confidence, and clicking it opens the model object.
Framing rule

A trained model is a dataset with a function attached — same lineage discipline, same version discipline, same quality evidence. Everything in this spec follows from treating it that way, and from reusing the run surface rather than inventing a second one.

3.2The four tracks

3.2.1 Train

Model families are presented as what they are for, never as architectures: language models (including reinforcement fine-tuning) for drafting, extraction and review; tabular AutoML for assay tables and clinical endpoints; diffusion for generative perturbation and augmentation; molecular property models for potency, ADMET and selectivity. The user picks a goal and a dataset; the family follows and is stated.

Training reuses the run surface verbatim — the same panel head, run bar, phase accordion and step views as a workflow (Spec 06). The phases differ; nothing about the chrome does. This is the single largest integration decision in the module: a scientist who has watched one workflow run already knows how to watch a training job, read its parameters, and open a step.

  • DatasetA dataset object from the user's data — the same object the workflows read and write. No separate ML data import.
  • TrainThe same cloud compute and the same live phase list as a run.
  • Quality gateHeld-out evaluation against a floor — AUC 0.81 vs 0.75 floor — not a leaderboard position.
  • TrackingEvery attempt recorded with its dataset version, parameters, metrics and artifacts.
  • RegisterThe trained model becomes a callable object with a name and a version.

3.2.2 Adapt

Adaptation is presented as a ladder of cost, not a technique menu, and each rung is independently switchable:

LevelCostWhat it holdsDefault
Prompt-level rulesCheapest · instantRules learned from repeated edits.On
Few-shot memoryCheap · seconds to indexBefore→after pairs indexed from real edits.On
Fine-tuned adapterCostly · a training jobWeights built from accumulated pairs.Off

The material of adaptation is the user's own editing. When someone rewrites "the compound showed good efficacy" into an effect size with a confidence interval, that edit is captured as a pair and a learned rule is proposed in plain language: "Replace qualitative efficacy claims with the effect size and its interval."

Consent rule

Adaptation is visible and reversible. Every rule shows the edit it came from, is scoped to a project or an organisation, and can be switched off. Nothing is learned silently, and no rule is applied that the user cannot read as a sentence.

3.2.3 Optimise

The closed loop, presented as rounds rather than as reinforcement learning. Each round is a row: what it proposed, what came back from the assay, and what the surrogate learned. The current round shows its proposals with confidence and gate verdicts.

ElementWhat it shows
Round listOne row per round: state, what happened, when. Round 1 is the baseline scored from literature only, so the loop's own progress is legible.
SurrogateWhich models are scoring, by name and version — admet-herg v3 + potency-gp v2 — each clickable to its model object.
Refit policyWhen the surrogate updates: automatic on every assay upload, with the last refit time.
Proposal tableCandidate, predicted properties, confidence, and a verdict: accepted, flagged by the safety gate, or rejected by it.
BudgetThe experimental budget the loop is optimising under — set by the user, not inferred.

The safety gate is the important element here. A proposal rejected by it is shown, with the reason, rather than filtered out of the list — a user must be able to see what the loop wanted to do and why it was not allowed to.

The loop’s hard part is not the model. It is the return path from the bench, specified in §3.7.

3.2.4 Run a pre-trained model new

BioMate integrates open-source models that arrive already fitted — structure prediction, genomic sequence models, chemical screening models. Nothing of the user's is trained. Until now the spec had no home for them: they are not "train your own", and burying them inside generic workflows hides both their confidence semantics and their specialised outputs.

Placement decision

Pre-trained inference lives in Models, as a fourth track — not as an unmarked Data-analysis workflow. The reason is the questions it raises. For a trained model the questions are "what did it learn from?" and "how did it score held-out?". For a pre-trained one they are "what can it speak to?" and "how much of this answer do I trust?" — model questions, answered by a model object, in the surface where models live. It still executes as a run, on the run surface, like everything else.

A pre-trained model object differs from a trained one in exactly two ways, and both are stated rather than hidden:

Trained herePre-trained
EvidenceHeld out on your data, against a floor.Published by its authors — plus a local spot-check on our own set, which is what actually earns it a gate here.
LineageInto a dataset version in this project.None into your data. The training corpus may be undisclosed, and that is recorded as a known gap rather than left blank.

Presentation follows the no-inventory rule: three domains, each stated as an achievement with what it produces and how long it takes — "predict a structure and tell me where to trust it", not a list of package names and versions on the front door. The model name and version are on the result, where they are accountable.

3.3The model object

The destination of every training run and the target of every prediction link. It is deliberately shaped like the dataset object (Spec 04), because a model is a dataset with a function attached.

SectionContents
IdentityName, version, family, confidence band, and how it got here — trained here, imported from your lab, or an external service under contract.
EvidenceThe held-out gate result against its floor, calibration, and the evaluation set as a dataset chip. A model with no held-out evidence cannot be registered.
LineageThe dataset version it learned from, the run that produced it, and every model version before it.
Used byEvery surface consuming it right now: workflow gates, score columns, DMTA rounds. This is the blast radius, and it is what makes a version bump safe to reason about.
InterfaceHow it is called: a Python scored() entry point, a container image, or a REST endpoint.
VersionsEvery version with its gate verdict. Superseding a version never deletes it; completed runs keep the version they used.

Earned surfaces

This last rule matters for legibility overall. A project's navigation reflects what that project does. Advertising every capability everywhere is how a platform becomes illegible — the cure for "I didn't know BioMate could do that" is not putting all of it on every screen.

3.5Bringing your own model

Three ways in, presented by what the user already has rather than by our plumbing:

  • Python functionA scored() entry point in your package. No container build; runs in the workflow sandbox.
  • ContainerYour own image and dependencies — for a fixed environment or GPU needs.
  • REST endpointA URL and a key, for vendor or internal services we do not host.

An imported model enters the same registry and is held to the same standard: it needs held-out evidence on a dataset in the product before it can be used in a gate. An external service under contract shows its contract end date, because a run that depends on it will break when the contract lapses.

3.7The wet-lab loop new

An optimisation loop whose scores never meet a measurement is a simulation of drug discovery. This section specifies the return path — the part that is not compute — because it is where this class of project actually fails: latency is measured in weeks, returns are partial, and the numbers come back censored.

3.7.1 A round is the contract

The loop does not consume a stream of results; it consumes rounds. A round has proposals out, an order to the bench, results back, and a refit. Its state is always visible as a stage bar.

Leaving the platform, a round becomes an order sheet and plate map in the format the lab registers from, pairing platform candidate ids with the lab's registry ids. Identity must survive the round trip or nothing downstream can be joined.

3.7.2 Three intake routes

RouteWhat it isFor
Drop an exportA plate CSV, ELN or LIMS export, mapped once with a template and auto-mapped thereafter.The common case, and the one that must work with no integration project.
ConnectorA LIMS or ELN API, polled on a schedule; each pull lands as a new dataset version.Organisations with a system of record.
Watched intakeA per-project address or an instrument folder.Instruments that can only email or write to a share.

All three land in the same place: a dataset object in the project, with the instrument or system as its origin and a version per pull (Spec 04 §4.5). There is no separate "assay results" store.

3.7.3 Mapping is a template, not a wizard

Mapped once per assay type and saved: compound identity via the order sheet, the readout column and its units, replicate handling, censoring, and the plate QC flag. Subsequent uploads map automatically. An upload that does not fit is held and shown as a diff — never coerced into the columns the loop was expecting. Editing a template affects future uploads only; results already ingested keep the mapping they were read with.

3.7.4 Partial returns are first-class

Anti-survivorship rule

Every proposal in a round is accounted for, including those that produced no number — not synthesised, insufficient material, assay QC failed — each with its reason. Dropping those rows would train the surrogate on survivors only, and it would quietly learn that everything it proposes gets made and assayed.

Return kindRecorded asEffect on the model
MeasuredA value with units and replicate spread.Trains normally.
CensoredIC50 > 30 µM, preserved as an inequality.Fitted as censored data — never coerced to 30, which would invent a measurement.
Not synthesisedThe reason — a route that failed, and where.Informs synthesisability, not activity.
Insufficient materialHow short, against the assay minimum.No activity signal; the proposal stays open.
Assay QC failedThe failing plate or control.Excluded, queued for repeat. Never averaged in.

3.7.5 Refit

One policy, stated once: partial refit at 50% returned, full refit on close. Partial results are useful, and waiting for the last two compounds wastes a week. The refit is a training run — it inherits the run surface, its gates and its audit trail, and it produces a new model version that does not score anything until it passes. The refit's effect is reported on held-out data ("surrogate MAE 0.41 → 0.33"), not on the new results it just learned from.

3.7.6 What the loop must show a reviewer

  • Predicted versus measured, per round. The only honest measure of whether the design pipeline works, and the thing a client will ask for first.
  • Which surrogate version scored which round. Every proposal traceable to a model version and an assay round.
  • Every rejection and every no-data return, with reasons.
  • The budget the loop is optimising under — set by the user, never inferred.

3.8Domain viewers for inference outputs new

The evidence classes (Spec 00 §0.7) choose the kind of viewer. These outputs need viewers specific to their science, because the generic one lets a user over-read the result — which is the exact failure mode this product exists to prevent.

3.8.1 Structure prediction

Three views of one output, shown together and never separately:

ViewReadsBehaviour
3D structureThe predicted fold.The familiar viewer. Alone, it is not a sufficient rendering of this output.
Per-residue confidence chartWhich parts of that picture to believe.A bar per residue, coloured by confidence band, with a mean. Linked to the 3D view: hovering reads out the residue and its score; clicking centres the structure on it. One selection, not two.
Pairwise error heatmapWhether the relative placement of two regions is resolved.A matrix; dark blocks are confident domains, a pale off-diagonal says their relative orientation is unresolved. Answers the question per-residue confidence cannot.

Beneath the chart, the low-confidence regions are listed in words — "Loop 43–57 · low confidence, flexible loop with no template coverage" — because a chart the user has to interpret unaided is only half a viewer. Each row centres the 3D view on that region.

Over-reading rule

A structure picture with no confidence chart invites a binding-site claim that its disordered loops cannot support. The chart is not an optional detail view; it is part of the output.

3.8.2 Genomic sequence models

Per-base scores render as tracks over the locus — model score, conservation, flagged intervals, variant ticks — sharing one coordinate axis. The actionable output is not the per-base vector but the flagged interval, so intervals are listed with their locus, their annotation context and why the model flagged them; the tracks are how a user checks the list rather than the list itself.

3.8.3 Chemical screening models

A ranked hit table, and a 2D depiction grid as an alternate view of the same ranking — a chemist reads structures, not identifier strings. Every score names the model and version behind it; a candidate outside the model's applicability region is held with no confident number offered. Specified with the ranking surface in Spec 05 §5.5.

3.9Copy rules

  1. No architecture names in primary copy. Families are described by what they are for. Architecture belongs in the model object's detail, for the reader who wants it. The same holds for integrated pre-trained models: named on the result, not on the front door.
  2. Published evidence is labelled as published. An author-reported benchmark is never presented as though it were measured here.
  3. No leaderboards. Gates and floors only. Never rank a user's models against each other.
  4. Never a bare prediction. Model, version and confidence travel with every predicted number.
  5. Adaptation speaks in sentences. A learned rule is stated as a rule, with the edit that taught it.
  6. A rejected proposal is shown. The loop's refusals are as informative as its suggestions.
