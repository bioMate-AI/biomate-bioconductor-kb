Files & the dataset object

BioMate · Function-module spec 04Status: for reviewSurface: Project → Files

Everything in BioMate is downstream of a file. This spec covers the project file system and the dataset object — the claim that a file is not an inert blob but an object with quality, versions, lineage and a list of everything that has consumed it. Two design commitments run through it: the object is attached to the familiar file, never a replacement for it; and history is append-only, so nothing a finished run consumed can change underneath it.

4.1Why a file becomes an object

Question a scientist actually asksA plain file systemThe dataset object
"Is this the version the figure came from?"Guess from the filename.The run records the exact version it read.
"Where did this file come from?"Ask a colleague.Origin, who added it, and the run that produced it.
"Can I trust it?"Open it and look.A quality verdict from ingest, with the specific notes behind it.
"What did we do with it?"Search chat history.Every run that read it, and everything those runs wrote.
"Someone edited it — what broke?"Unanswerable.Versions, a diff, and which runs pinned which version.
Attachment rule

The object does not replace the file. Users still see folders, filenames and extensions, and can still open the thing in Jupyter. Everything the object adds hangs off that familiar row — because a tool that renames the user's mental model to "dataset entity" loses before it starts.

4.2.3 Scope: project, shared, account

A file lives in a project by default. It can be promoted to account scope — shared/ — and then used from any project without re-uploading: still one file, one version history, one lineage. Demoting it back restricts new use, and other projects keep a read-only reference to the version they already consumed. A content hash means the same file added twice links to one entry rather than creating two.

4.3The dataset object — Preview shipped

Tab one answers "what is in it". Three views over the same bytes, plus editing.

ViewShowsNotes

Append-only rule

Saving an edit writes a new version. It never overwrites. The copy says so at the moment of editing — "saving writes v4 and leaves earlier versions intact, so a completed run always keeps the exact bytes it consumed". This is the single most important sentence in the file system, because it is what makes the rest of the audit trail true.

Below the preview, a stat grid: rows, columns, size, current version, and any domain-specific summary the ingest produced.

4.3.1 Open in

The object header offers the environments that fit the file — Jupyter (Python, pandas, scanpy), RStudio (R, tidyverse, DESeq2), a plot viewer, and Ask in chat. A session mounts the current version read-write; saving from that session writes a new version, exactly as an in-place edit does. Environments are offered by file type, so a VCF gets bcftools and a terminal rather than a plotting kernel.

4.5The dataset object — Where it came from shipped

4.5.1 Origin

Type (upload, run output, database pull, shared), a human label, who added it and when, and a note about how. If it was produced by a run, Open the run that produced it → goes straight to that run surface. The content hash is shown, with the deduplication behaviour stated plainly. Visibility — this project or the whole account — is a two-button control here, with the consequence written next to it rather than in a help article.

4.5.2 Quality, at ingest

Quality is assessed when the file arrives, not when a run fails. The verdict is one of three, and it always comes with the specific notes that produced it.

VerdictMeaningConsequence
GoodNothing found that should stop use.None.
WatchSomething specific is wrong — a missing batch column, two spellings of one level, an outlier depth.Runs can still use it; outputs inherit the amber verdict.
BlockedUnusable as-is — malformed, or a licence not accepted.Cannot be an input until resolved.
Inheritance rule

Anything produced from an amber input stays amber until a human clears it. A figure built from a watch-flagged table carries the flag. This is what stops a quality problem from being laundered by three steps of processing.

4.5.3 What used it, and what came out

The lineage section, and the reason the object exists. Every run that read the file, with its status, the version it read, and its gate summary — and beneath it, everything those runs produced, each output typed by evidence class (Spec 00 §0.7) and openable. Outputs that are themselves datasets — a counts matrix, a DE results table — open as dataset objects, which is how lineage chains without a separate lineage viewer. Training runs appear in this same list alongside workflow runs: one history, not two (Spec 03 §3.4).

Export for deposit emits an RO-Crate: source, checksums, versions, runs, parameters, software and outputs — the archive a journal or a regulator asks for, assembled from what the object already knows.

4.6Ingest new

The moment that determines whether everything downstream is trustworthy. Three sources, one outcome.

  • Drop a fileLocal upload. Parsed, typed and profiled on arrival.
  • Paste a URLFetched, with the source URL retained as origin.
  • Pull from a databaseFrom a connector configured for the account; the query and the corpus version are retained as origin.

In all three cases ingest produces the quality card before anything runs: detected type, row and column counts, the column profile, and the specific notes. The user sees what BioMate thinks the file is, and can correct a mis-detected column mapping then — which is far cheaper than discovering it in a 40-minute run's phase C.

4.9Copy rules

  1. Say "file", show the object. Never make the user learn a new noun for their data.
  2. Version changes are described in words. What changed, not which bytes.
  3. A quality verdict always carries its evidence. A dot with no notes behind it is a rumour.
  4. State the consequence at the control. Scope buttons, edit saves and restores all say what will happen next to them.
  5. Amber travels. Inherited quality is shown on the descendant, not only on the ancestor.
