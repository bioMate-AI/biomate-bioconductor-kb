The workflow panel

BioMate · Function-module spec 07Status: for reviewSurface: right panel, or full width

Where a run is configured, watched, gated and read. It is one structure used by everything expensive the platform does — validated workflows, model training, pre-trained inference and design runs all render here, because a scientist who has watched one run already knows how to read the next. This spec covers its three sections, the two kinds of gate that can stop it, and the two records it leaves behind.

Blocker rule

A disabled primary action must carry its reason next to itself, with the remedy. A blocker explained three screens up in an input slot is a dead end: the user sees a greyed button and no cause. This is the general form of Spec 04 §4.9's "state the consequence at the control".

7.2Workflow settings

Everything decided before the run, in one place, in the order a user needs it.

  1. Clarification, if the configuration is underdetermined — the typed confirm-inference card (Spec 06 §6.4). It appears first because everything below it may depend on the answer.
  2. Global parameters, as .param-rows: name, resolved value, and a provenance badge — see §7.4.
  3. Inputs, resolved from the project's files rather than uploaded (Spec 02 §2.4.2).
  4. Phases to run, with the three skip states (Spec 02 §2.5.1).
  5. Your permissions here and the verification pattern — §7.3.

Auto-loop on QC failure sits with the parameters: retry a failed phase with adjusted parameters, capped at three attempts, with a review window before each retry. It is on by default and always visible, because a system that silently retries is a system whose results cannot be reasoned about.

7.3Permissions in the panel

The panel states the current user's role and what it permits, on the surface where the consequential actions live (Spec 00 §0.12). Each capability row names the role it needs and whether the user has it. Controls beyond the user's role are disabled with the role named, never hidden.

Alongside it, the verification pattern is stated once: the five checks in the product, what measures each, and what a failure stops. It is here rather than in a help article because this is the panel where four of the five appear.

7.4Resolved parameters and their origins

A parameter row shows the value the run will actually use, and where that value came from. The origin is the point: a user must be able to tell what they chose from what was chosen for them.

OriginMeans
defaultThe workflow's own default, unchanged.
inheritedFrom a project instruction — a standing rule the user wrote, possibly weeks ago. Accent-styled, because this is the origin users are most surprised by.
recommendedBioMate proposed it for this data, with a reason and a citation behind why.
confirmedAnswered by the user in a clarification card, bound to this field.
editedChanged by hand in this configuration.

why expands one line of justification plus its citation. Every recommended value must have one; a recommendation with no reason is a default wearing a costume.

7.5Phases, steps and the quality gate

The accordion. Each phase carries its letter, name, step count, duration and state chip; each step carries its name, status, and — once it has run — its tool and version, its two headline parameters, and its outputs as evidence-badged chips. A step offers three actions: edit its parameters, re-run from here, and Full view (Spec 08).

7.5.1 The quality gate

A gate halts the run and takes over the top of the Phases section. Its anatomy is the verification pattern made concrete:

  • Measured rows: the metric, the observed value, the threshold.
  • Evidence level: what kind of claim the threshold rests on.
  • Suggested change: a before/after diff, with a rationale.
  • Three actions: apply the suggestion, keep my parameters, cancel the run.
Override rule

Keeping your parameters is always available, and always recorded as an override in the QC audit with the measurement that was overridden. Overriding requires the Reviewer or Owner role. A gate a user cannot override is a gate they will work around outside the platform; a gate they can override silently is not a gate.

The collapsed QC gates block under a phase shows every threshold for that phase in one reading — metric, operator, threshold, observed, verdict — including the ones that passed, so a reader can see what was checked and not only what failed.

7.6Human approval new

A machine gate asks "does the data meet the threshold?". Some decisions are not of that kind: spending beyond a budget, overwriting a version other runs read, signing off before something leaves the platform. Those need a person, and until now the panel had no way to ask for one — only the licence blocker and the pre-run confirmation, both of which are narrower.

ElementRequirement
whatThe action, in one line, in the user's terms.
whyWhy it needs a human — the threshold crossed, the thing overwritten, the irreversibility.
costWhat it will cost and what it will write — money, time, versions, notifications. Never omitted, never rounded away, and it must describe the action actually being gated, not a related one.
measured rowsThe same three columns as a QC gate. This is deliberate and not negotiable.
whoWhether this user can approve it, and the policy behind that — "publishing to the project record requires an owner".
Approve / Deny / Ask a reviewerApproving records the approver, the timestamp and the reason shown. Denying leaves the run paused with nothing written. Delegating leaves it paused until someone with the role answers.
Approval rule

An approval pauses; it never proceeds on a timeout. A pause that resolves itself by waiting is not an approval, and would be worse than having none — it would produce an audit trail that claims a human agreed when no human read it.

Where approvals arise: publishing outputs into the project record where other runs read them, spend above a project threshold, registering a model that gates a live campaign, and any step that sends data or an order outward. The same component serves all four.

Truthfulness rule

The what, why, cost and measured rows must describe the action at the point the run actually paused. An approval card that describes a plausible-but-different action — a re-run, when what is being gated is this run's final write — produces an audit record asserting a human agreed to something nobody was asked about. That is a worse failure than having no approval gate at all.

7.7The agent trajectory new

The panel's provenance was, until now, entirely data-side: which file, which version, which parameter, which output. That answers "where did this number come from" and leaves unanswered a question users ask just as often — "why did it do it this way?" The trajectory is the agent-side complement to lineage, and it is a tab of the after-run report.

Entry kindRecords
DecisionThe routing verdict and its reasoning in the user's terms — "read the goal as a standardised differential-abundance analysis; chose the validated lane because the goal named a figure".
Tool callWhat was called, with timing and a result count. Nested calls nest.
Your answerEvery clarification and every gate decision, with the field or parameter it bound to.
What it told youThe mid-run progress lines and the post-run reply, verbatim (Spec 06 §6.9).
GateWhere a gate or approval paused the run, and what was surfaced rather than decided.

Filterable by kind, exportable with the audit trail. Two design decisions worth stating:

  • The assistant's own words are in the record. If it narrated it, it is auditable — which is also what stops narration drifting into reassurance the evidence does not support.
  • It is written in the user's terms, not the system's. A trace of prompts and token counts serves an engineer debugging the harness; a scientist needs to know which decision to disagree with. Timing and call names are enough machinery; the reasoning is prose.

7.8After run

Three tabs. Summary combines the run report and findings, with every number linked to the output in which it is findable (Spec 08 §8.6). Outputs lists every artifact by producing step, evidence-badged, with dataset-class outputs opening as dataset objects. Reproducibility record keeps Methods, resolved Parameters, Software, Citations, QC audit and Trajectory as expandable sections. Nothing is removed; the record stops competing with the primary result for attention.

7.9States

7.10Copy rules

  1. Every state has a word, not only a colour or a bar.
  2. A blocker sits at the control it blocks, with its remedy.
  3. A parameter states its origin. Inherited values are the ones users most need to see.
  4. All five checks read the same way — measured, threshold, verdict.
  5. An override is recorded, never prevented.
  6. An approval waits. No timeouts, no defaults, no implied consent.

7.11Open questions

  • open Whether a denied approval should offer a reduced alternative automatically — "re-run on the 84-sample subset for £160" — or leave that to the user.
  • open How the trajectory should render a long agentic run with hundreds of tool calls without becoming a log nobody reads.
  • open Whether auto-loop retries should each appear in the trajectory, or collapse into one entry with an attempt count.
  • open Whether approvals should be answerable from outside the panel — a notification, an email — for a reviewer who does not live in the product.
