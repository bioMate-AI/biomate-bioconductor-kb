Worked examples: model use cases

BioMate · Spec 10 · addendum to Spec 03Status: builtLane: Cloud

The Models module had a registry, a training surface and a loop, but no page that showed a model use case end to end. This addendum specifies four worked cases — one per track — on a single spine: what model, what it was given, what came back, how much of the answer to trust, and what it left behind. It also renames two tracks whose labels named techniques instead of jobs.

10.1Track renames

Adapt fine-tuneTune on our data base frozen, your delta kept separate"Adapt" covered two unrelated jobs: fine-tuning a scientific model, and learning how BioMate writes. The lane now states what the user controls, not the algorithm.
Optimise RL & active learningPropose & test in rounds a budget you set, not an algorithm you pickReinforcement learning is machinery. The user's job is rounds under a budget, with a bench round-trip in the middle.
Models tab "Adapt"Models tab House styleThat surface learns wording and house conventions from your edits. It states explicitly that it never changes a predicted number, and points to Tune on our data for the scientific case.
Rule

A user-facing label names a job. Techniques (LoRA, active learning, Bayesian optimisation) appear in the run's Methods, where they are checkable, not in navigation, where they are jargon.

10.4Case page anatomy

ElementBehaviour
model chipName and version, as a link into the model object. Only names that exist in the registry may appear here.
what this was givenInputs resolved to versions, plus the decision each row encodes and why. Includes what was excluded and on what rule.
stagesThe run's phases as chips. Before the result exists they read "waiting"; nothing is reported until the evaluation stage finishes.
what came backA headline sentence, then labelled blocks. One block is always the honest one — what it learned that you may not want, the flag, or the round still in flight.
boundaryWhat the result is not evidence for. Present on all four cases.
floor tableMetric · value · threshold · pass/flag. A floor, not a ranking; clearing it by more does not make a model better.
artefactsEach artefact is a file in the project. Reports get "Open & edit" plus the download menu; tables and model artefacts get "Open in Files".
next stepsDecisions, never automatic actions: register, open the model object, open the report, or run the thing the result recommends.
register newWrites to the registry through one helper: the registry row and the model card both move, the previous version is marked superseded rather than deleted, and every surface re-reads live. The toast and the registry can no longer disagree.

10.5Registry additions

Two models were added so that every case names an object that can be opened: fold-predict v2.3 (pre-trained protein structure, weights pinned, benchmark evidence re-runnable by us) and molgen v4.1 (public generative base; your adapter recorded as a delta, never merged into the base, with the adapter as a call argument so base behaviour stays reachable). Each has full evidence, lineage, consumers, interface and version history.

10.6Case reports

Each case leaves its own report — fold_report.md, train_report.md, adapt_report.md, loop_report.md — in runs/models/, each with its own sections, versions and edit proposals. No case borrows another run's document.
