Reports as editable files

BioMate · Spec 12 · addendum to Specs 04 & 07Status: builtObject: document

A run produced a report and the report stayed on the run. You could read it; you could not take it, edit it, or find it again through Files. This addendum makes a report a file object — downloadable in the formats people actually hand over, editable by hand, editable by asking, versioned, and present in the project file list with everything else.

12.1What changed

BeforeNow
After-run opened on Outputs; the report was a "Download report" link that only toasted.After-run opens on a Report tab holding the document itself, with a real download menu and "Open in Files".
Reports were not in the file tree.Six documents are file objects: the after-run report, a saved search answer, and one report per model case in runs/models/.
No editing of any kind.Hand editing in place, and chat-based editing that proposes a before/after diff you accept or reject.
—Data files get the same ask-and-diff affordance at cell level.

12.2Download

FormatWhat it is
PDFTypeset from the project memo template.
Word (.docx)Styles mapped, comments preserved.
Markdown (.md)The source the document is stored as.
HTMLSelf-contained, figures inlined.
Report bundle (.zip)Report + every output + run manifest + checksums.
Rule

The bundle is the honest format: a report without its outputs and its manifest is not reproducible. Every format carries the run id and the version being viewed, so a downloaded copy can be traced back.

12.3Editing

12.3.1 By hand

Edit turns the page into editable prose in place. Saving writes a new version; it never overwrites what the run produced. A "Revert to v1" control returns the document to the run's original.

12.3.2 By asking new

ElementBehaviour
ask fieldFree text, plus the document's own suggested edits as chips. A used chip is marked done.
proposalThe exact paragraph now, the exact paragraph proposed, and why — one sentence naming the reader problem it solves.
acceptApplies and saves as a new version; the previous version stays, and the run keeps pointing at the one it produced.
rejectDiscards. Nothing was written.
ask againRe-drafts against the same paragraph with a correction ("shorter", "more cautious", "keep the number").
data filesSame control, cell-level diff: row · field · now · proposed. Accepting writes a new file version; runs that read the old one keep pointing at it.

12.4Versions — one source of truth

Document edits and file history are the same history. fileVersions(id) merges any accepted document edits onto the file's stored versions, and every surface reads through it: the file row badge in the tree, the object header badge, the file's Versions tab, and the document header. A change event re-renders the tree and header on accept.

Rule

Two surfaces may never state different current versions of one object. The failure this rule prevents was live: the file list read v1 while the open document read v2, in a product whose premise is that nothing is silently overwritten.

12.5One control per screen

The document component and its host both used to render a version chip, a download menu and an in-Files link, so every report screen showed each control twice. Ownership is now explicit: in Files the object header owns the version chip and Download (the document keeps only Edit / Save); on the run's Report tab the document owns them, and the After-run strip carries no duplicate.

Each carries a quality badge and quality notes — the tuned-model report is watch, because it inherits a novelty flag that constrains how the model may be used — plus an origin note stating that it keeps the model or run version that produced it, so an old report stays readable after that model is superseded.
