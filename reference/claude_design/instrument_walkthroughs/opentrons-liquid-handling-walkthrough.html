Liquid handling — drive the robot, measure elsewhere

Drive your pipetting robot to prepare a plate — the analysis comes later.

Your Opentrons OT-2 or Flex is a liquid-handling robot: it moves precise volumes between wells to dilute samples or lay out a plate. BioMate can generate a protocol, upload it, start the run, and monitor it — but the robot produces a prepared plate, not a dataset.

It measures nothing, so there is no result file for BioMate to analyse on the robot — the science happens on whatever instrument measures that plate next.

Protocol→ Robot runs it→ Prepared plate→ Measured & analysed elsewhere
The problem

A prepared plate is not a result — and the robot measures nothing.

The robot moves liquid between wells; it does not measure anything. So there is no “result file” for BioMate to interpret on its own — and, confirmed in the connector code, the Opentrons connector maps the robot to no analysis workflow. This tutorial will not invent an analysis the robot cannot produce.

1 · NOT A DATA INSTRUMENT

Hardware output, not a file

It dilutes samples and lays out plates. The real product is a physical prepared plate — not a measurement, not a dataset.

2 · NO WORKFLOW MAPPING

Confirmed in the connector

Every other instrument connector maps its output to a workflow; the Opentrons connector only runs protocols — upload, start, check status.

3 · FIRST LINK IN A CHAIN

Prepare → measure → analyse

The science happens on the instrument that measures the plate. The robot just makes it; the analysis lives downstream.

BioMate drives the first link and runs the last; the measurement in the middle happens on the measuring instrument.

By design — the robot produces no analysis
The ideas you need first

Four ideas behind driving a liquid handler.

From a pipetting task to a prepared plate is a short, deliberate chain. These four ideas cover what BioMate does — and does not — with the robot.

1 · PROTOCOL

The instruction list

A short Python protocol naming the labware (plates, tip racks), the pipette, and the transfers — which volume goes from which well to which well.

2 · PROTOCOL EXECUTION

BioMate's actual job

Upload a protocol and drive the run. That is the capability the connector supports — not an analysis.

3 · RUN STATUS

The robot's honest report

idle / running / succeeded / failed / stopped — the robot's own account of how the run went.

4 · PLATE-MAP

Which well holds what

An optional CSV or JSON some protocols write. Bookkeeping about layout — not a measurement.

Step 1 · What you provide

A protocol, a reachable robot, and execution turned on.

Once the robot is registered (see Tutorial 6), BioMate can see and Check it. To actually drive a run you also need a protocol and the admin-enabled execution path over your lab network.

1 · A PROTOCOL

Generated or your own

BioMate can turn a simple well-to-well transfer into a protocol, or you upload a .py protocol your lab already validated on this robot.

2 · A CONNECTED ROBOT

Online in Connectors

Registered under Connectors → Instruments (type Opentrons, host/IP + port — default 31950), showing Online after you press Check.

3 · ADMIN-ENABLED EXECUTION

Driving vs. seeing

Registering lets BioMate see it; actually running a protocol over your lab network is enabled by your admin. Confirm it is turned on.

Residency is on-prem — the robot and its run records stay inside your network.

A protocol, a connected robot, execution enabled
Step 2 · How a run works

Describe the transfer — review it — then confirm.

Describe the task in plain English, the way you would to a colleague — for example, “On the OT-2 at bench 3, transfer 50 µL from each well of the source plate to the matching well of the destination plate,” or attach your own .py protocol.

Plain request / your .py→ Review labware, pipette, transfers→ Confirm & run→ Robot pipettes (watch status)
  • BioMate drafts the protocol. A simple well-to-well transfer becomes a protocol listing the labware, pipette, and transfers — or you attach a validated .py of your own.
  • You review before anything moves. Labware names, the pipette, and the transfer list are shown — catch a wrong volume or a swapped well before the robot runs. Nothing is sent until you confirm.
  • Then Confirm & run. BioMate uploads to the robot and starts it; status moves running → succeeded / failed / stopped. On failure the robot's own error is shown — fix the deck and run again.
Admin-enabled — but nothing moves until you confirm
Step 3 · The result — a plate and a record

Status and a record you keep — then measure the plate elsewhere.

Because the robot measures nothing, the result is the prepared plate plus the robot's run record. The data that feeds a BioMate workflow comes from the instrument that measures the plate next.

  • Status: succeeded means every pipetting step completed; failed / stopped did not, shown with the robot's own error text.
  • The record: the list of steps the robot performed, with timestamps — and, if your protocol wrote one, a plate-map CSV/JSON saying which well holds which sample.
  • Measured elsewhere: the prepared plate is the input to a plate reader, sequencer, or screen — and that measurement feeds the real BioMate workflow.
  • Keep the plate-map — it is how you will label the measurements the downstream instrument produces.
A plate and a record — not a measurement
Step 4 · Reading and trusting it

Honest limits: no analysis, admin-gated runs, and chemistry that is yours.

What makes this instrument trustworthy is precisely that BioMate does not over-promise. Read these limits before you rely on it.

  • No analysis workflow — by design. The connector runs protocols and reports status; it does not map to any BioMate analysis. Anyone who says “point BioMate at your OT-2 and get an analysis” is wrong about this machine.
  • Execution depends on admin setup. Registering lets BioMate see and Check the robot; actually driving it over your lab network is admin-enabled — confirm it is on before relying on it.
  • BioMate does not validate your chemistry. It faithfully runs the protocol you confirm. It does not know whether 50 µL is right for your assay — you do. Review carefully.
  • Status is honest. A failed run is reported as failed, with the robot's error — BioMate does not pretend a run succeeded.
Honest about what it is — and isn't
The habit at a glance

Design the protocol → review it → run it on the robot → measure the plate elsewhere → analyse that measurement.

The value is honest and narrow: BioMate drives your robot to make exactly the plate you designed and captures a record of what it did — then hands off to the instrument that measures it, where the real analysis lives.
