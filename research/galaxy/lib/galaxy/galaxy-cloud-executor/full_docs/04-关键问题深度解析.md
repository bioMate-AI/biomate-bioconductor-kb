## 问题1: Instance Profile 缺少角色

### 问题现象

**错误信息**:
```
NoSuchEntity: An error occurred (NoSuchEntity) when calling the CreateComputeEnvironment operation:
Instance Profile ecsInstanceRole cannot be found
```

或者:
```json
{
  "InstanceProfile": {
    "Path": "/",
    "InstanceProfileName": "ecsInstanceRole",
    "InstanceProfileId": "AIPXXXXXXXXXXXXXXXXXX",
    "Arn": "arn:aws:iam::399683337364:instance-profile/ecsInstanceRole",
    "CreateDate": "2024-10-14T10:00:00Z",
    "Roles": []  // ⚠️ 空数组!
  }
}
```

### 根本原因

AWS IAM 中，**Instance Profile** 和 **Role** 是两个独立的实体：

```
┌─────────────────────────┐
│   IAM Role              │
│   (ecsInstanceRole)     │
│   - 定义权限            │
│   - 信任策略            │
└─────────────────────────┘
           │
           │ 需要关联
           ↓
┌─────────────────────────┐
│   Instance Profile      │
│   (ecsInstanceRole)     │
│   - EC2 使用的容器      │
│   - 可以包含多个 Role   │
└─────────────────────────┘
```

**常见误区**:
- 以为创建 Role 后 Instance Profile 自动包含它
- 使用控制台创建时 AWS 会自动关联
- 使用 CLI/脚本创建时**必须手动关联**

### 诊断方法

```bash
# 检查 Instance Profile 是否存在
aws iam get-instance-profile --instance-profile-name ecsInstanceRole

# 检查 Roles 数组
aws iam get-instance-profile \
  --instance-profile-name ecsInstanceRole \
  --query 'InstanceProfile.Roles' \
  --output json

# 如果输出是 [] 或 null，说明缺少关联
```

### 解决方案

```bash
# 将 Role 添加到 Instance Profile
aws iam add-role-to-instance-profile \
  --instance-profile-name ecsInstanceRole \
  --role-name ecsInstanceRole

# 验证
aws iam get-instance-profile \
  --instance-profile-name ecsInstanceRole \
  --query 'InstanceProfile.Roles[0].RoleName' \
  --output text

# 应该输出: ecsInstanceRole
```

### 预防措施

**方法 1: 使用脚本自动化**
```bash
# 在创建脚本中添加验证
create_instance_profile() {
    aws iam create-instance-profile --instance-profile-name "$1"
    aws iam add-role-to-instance-profile --instance-profile-name "$1" --role-name "$1"

    # 验证
    ROLE_COUNT=$(aws iam get-instance-profile \
        --instance-profile-name "$1" \
        --query 'InstanceProfile.Roles | length(@)' \
        --output text)

    if [ "$ROLE_COUNT" -eq 0 ]; then
        echo "❌ Error: Role not added to Instance Profile"
        exit 1
    fi
    echo "✅ Instance Profile created and role added"
}
```

**方法 2: 使用 CloudFormation/Terraform**
- 这些 IaC 工具会自动处理关联

## 问题2: 实例类型在特定 AZ 不可用

### 问题现象

**错误信息** (在 ASG Activity History 中):
```
Launching a new EC2 instance. Status Reason: Your requested instance type (m4.large)
is not supported in your requested Availability Zone (us-west-2d). Please retry your
request by not specifying an Availability Zone or choosing us-west-2a, us-west-2b,
us-west-2c.
```

**观察到的行为**:
1. 作业进入 RUNNABLE 状态
2. ASG 尝试启动实例
3. 启动失败，显示上述错误
4. AWS Batch **自动重试**其他 AZ
5. 在 us-west-2a 成功启动

### 根本原因

**AWS 实例类型可用性**:
- 不同代的实例类型在不同 AZ 的可用性不同
- **旧代实例** (m4, c4) 在**新 AZ** (us-west-2d) 通常不可用
- **新代实例** (m5, c5) 在所有 AZ 可用

**为什么会遇到这个问题**:
- AWS Batch 默认配置可能选择 m4.large
- us-west-2d 是较新的可用区（2018年后添加）
- m4.large 是第4代实例（2015年发布）

### 实例类型和 AZ 兼容性

| 实例系列 | 发布年份 | us-west-2a | us-west-2b | us-west-2c | us-west-2d |
|---------|---------|-----------|-----------|-----------|-----------|
| m4.large | 2015 | ✅ | ✅ | ✅ | ❌ |
| m5.large | 2017 | ✅ | ✅ | ✅ | ✅ |
| m6i.large | 2021 | ✅ | ✅ | ✅ | ✅ |

### 诊断方法

```bash
# 查看 ASG Activity History
ASG_NAME=$(aws autoscaling describe-auto-scaling-groups \
  --query 'AutoScalingGroups[?contains(AutoScalingGroupName, `galaxy-cloud`)].AutoScalingGroupName' \
  --output text)

aws autoscaling describe-scaling-activities \
  --auto-scaling-group-name "$ASG_NAME" \
  --max-records 10 \
  --query 'Activities[*].{Time:StartTime,Status:StatusCode,Message:StatusMessage}'

# 查看实例类型配置
aws batch describe-compute-environments \
  --compute-environments galaxy-cloud-compute \
  --query 'computeEnvironments[0].computeResources.instanceTypes'
```

### 解决方案

**方案 1: 使用 "optimal" (推荐)**
```bash
# 让 AWS Batch 自动选择最优实例类型
aws batch update-compute-environment \
  --compute-environment galaxy-cloud-compute \
  --compute-resources instanceTypes=["optimal"]
```

**方案 2: 指定新代实例**
```bash
# 使用 m5/m6i 等新代实例
aws batch update-compute-environment \
  --compute-environment galaxy-cloud-compute \
  --compute-resources instanceTypes=["m5.large","m5.xlarge"]
```

**方案 3: 限制可用区**
```bash
# 只使用支持旧实例类型的 AZ
aws batch update-compute-environment \
  --compute-environment galaxy-cloud-compute \
  --compute-resources subnets=["subnet-xxx","subnet-yyy"]
# 确保这些 subnet 在 us-west-2a/b/c
```

### 为什么这个问题会自动解决？

AWS Batch 的**自动重试机制**:
```
1. 尝试在 us-west-2d 启动 m4.large → 失败
2. 标记 us-west-2d 为不可用
3. 尝试在 us-west-2a 启动 m4.large → 成功
4. 后续作业优先使用 us-west-2a
```

**所以你不需要手动干预！**

### 预防措施

1. **使用 "optimal"**（强烈推荐）
   - AWS Batch 会选择最佳的实例类型和 AZ 组合
   - 自动适应可用性变化

2. **避免指定旧代实例类型**
   - 不要硬编码 m4, c4, r4 等
   - 使用 m5, m6i 等新代实例

3. **监控 ASG Activity**
   - 设置 CloudWatch 告警监控启动失败

## 问题3: Launch Template 缺少 IAM Instance Profile

### 问题现象

**症状**:
1. 作业进入 RUNNABLE 状态
2. ASG DesiredCapacity 更新为 1
3. EC2 实例成功启动
4. **实例几秒后变成 `terminated` 状态**
5. 在 EC2 控制台查看实例：
   - IAM Profile: "未设置" 或 "None"
   - 状态: terminated

**EC2 实例详情**:
```
Instance ID: i-0123456789abcdef0
State: terminated
IAM instance profile: -           ⚠️ 没有!
Launch time: 2024-10-14 10:00:00
Termination time: 2024-10-14 10:00:15  ⚠️ 15秒后终止
```

### 根本原因

**Launch Template 配置不完整**:

AWS Batch 在创建 Compute Environment 时会自动创建 Launch Template，但有时会**漏掉 IamInstanceProfile 字段**。

**正确的 Launch Template 配置**:
```json
{
  "LaunchTemplateData": {
    "ImageId": "ami-xxx",
    "InstanceType": "...",
    "IamInstanceProfile": {              // ⚠️ 这个字段可能缺失!
      "Arn": "arn:aws:iam::xxx:instance-profile/ecsInstanceRole"
    },
    "SecurityGroupIds": [...],
    "UserData": "..."
  }
}
```

**缺少 IamInstanceProfile 的后果**:
```
EC2 实例启动
  ↓
ECS Agent 尝试注册到 ECS Cluster
  ↓
需要 AWS API 凭证 (从 Instance Profile 获取)
  ↓
❌ 没有 Instance Profile
  ↓
ECS Agent 无法获取凭证
  ↓
ECS Agent 注册失败
  ↓
实例无法加入 ECS Cluster
  ↓
Compute Environment 认为实例不健康
  ↓
实例被终止
```

### 诊断方法

#### 步骤 1: 检查实例状态

```bash
# 查看最近的实例
aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=*galaxy-cloud*" \
  --query 'Reservations[*].Instances[*].{ID:InstanceId,State:State.Name,IamProfile:IamInstanceProfile.Arn,LaunchTime:LaunchTime}' \
  --output table

# 如果 IamProfile 列为空，说明有问题
```

#### 步骤 2: 检查 Launch Template

```bash
# 查找 Launch Template
LT_ID=$(aws ec2 describe-launch-templates \
  --filters "Name=tag:Name,Values=*galaxy-cloud*" \
  --query 'LaunchTemplates[0].LaunchTemplateId' \
  --output text)

# 检查 IamInstanceProfile
aws ec2 describe-launch-template-versions \
  --launch-template-id "$LT_ID" \
  --versions '$Latest' \
  --query 'LaunchTemplateVersions[0].LaunchTemplateData.IamInstanceProfile'

# 如果输出为 null，说明缺失
```

#### 步骤 3: 查看实例日志 (可选)

```bash
# 获取实例控制台输出
INSTANCE_ID=$(aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=*galaxy-cloud*" \
  --query 'Reservations[0].Instances[0].InstanceId' \
  --output text)

aws ec2 get-console-output --instance-id "$INSTANCE_ID"

# 查找 ECS Agent 相关错误
```

### 解决方案

#### 方法 1: 使用提供的脚本

```bash
bash lib/galaxy/galaxy-cloud-executor/scripts/fix_launch_template.sh
```

#### 方法 2: 手动修复

```bash
# 1. 获取 Instance Profile ARN
INSTANCE_PROFILE_ARN=$(aws iam get-instance-profile \
  --instance-profile-name ecsInstanceRole \
  --query 'InstanceProfile.Arn' \
  --output text)

# 2. 获取 Launch Template ID
LT_ID=$(aws ec2 describe-launch-templates \
  --filters "Name=tag:Name,Values=*galaxy-cloud*" \
  --query 'LaunchTemplates[0].LaunchTemplateId' \
  --output text)

# 3. 获取当前 Launch Template 配置
aws ec2 describe-launch-template-versions \
  --launch-template-id "$LT_ID" \
  --versions '$Latest' \
  --query 'LaunchTemplateVersions[0].LaunchTemplateData' > /tmp/current-lt.json

# 4. 添加 IamInstanceProfile 字段
# 编辑 /tmp/current-lt.json，添加:
# "IamInstanceProfile": {
#   "Arn": "$INSTANCE_PROFILE_ARN"
# }

# 5. 创建新版本
aws ec2 create-launch-template-version \
  --launch-template-id "$LT_ID" \
  --launch-template-data file:///tmp/current-lt.json

# 6. 更新 ASG
ASG_NAME=$(aws autoscaling describe-auto-scaling-groups \
  --query 'AutoScalingGroups[?contains(AutoScalingGroupName, `galaxy-cloud`)].AutoScalingGroupName' \
  --output text)

NEW_VERSION=$(aws ec2 describe-launch-template-versions \
  --launch-template-id "$LT_ID" \
  --query 'LaunchTemplateVersions[0].VersionNumber' \
  --output text)

aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name "$ASG_NAME" \
  --launch-template LaunchTemplateId="$LT_ID",Version="$NEW_VERSION"
```

### 验证修复

```bash
# 提交测试作业，然后检查新实例
aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=*galaxy-cloud*" "Name=instance-state-name,Values=running" \
  --query 'Reservations[0].Instances[0].{State:State.Name,IamProfile:IamInstanceProfile.Arn}'

# 应该看到:
# State: running
# IamProfile: arn:aws:iam::399683337364:instance-profile/ecsInstanceRole

# 检查 ECS 注册
# (需要知道 ECS Cluster 名称)
aws ecs list-container-instances --cluster <cluster-name>
# 应该能看到实例 ARN
```

### 为什么会出现这个问题？

**AWS Batch 的 Bug**:
- AWS Batch 在某些情况下创建 Launch Template 时会漏掉 IamInstanceProfile
- 这是一个已知问题，但 AWS 尚未完全修复
- 通常发生在通过 API/CLI 创建 Compute Environment 时
- 通过控制台创建通常不会有这个问题

### 预防措施

1. **创建后立即验证**
   ```bash
   # 在创建 Compute Environment 后运行
   bash scripts/check_integration_ready.sh
   ```

2. **使用 IaC 工具**
   - CloudFormation/Terraform 可以显式指定 Launch Template
   - 避免依赖 AWS Batch 自动创建

3. **监控实例状态**
   - 设置告警监控实例快速终止

## 问题4: AWS 凭证过期

### 问题现象

**错误信息**:
```python
botocore.exceptions.ClientError: An error occurred (InvalidClientTokenId) when calling
the DescribeJobQueues operation: The security token included in the request is invalid.
```

或:
```
botocore.exceptions.NoCredentialsError: Unable to locate credentials
```

### 根本原因

AWS 凭证失效的常见原因:

1. **临时凭证过期**
   - 使用 STS AssumeRole 获取的临时凭证
   - 通常 1-12 小时有效期

2. **Access Key 被禁用/删除**
   - 在 IAM 控制台手动禁用
   - 密钥轮换时删除旧密钥

3. **凭证文件损坏**
   - `~/.aws/credentials` 文件格式错误
   - 文件权限问题

4. **环境变量冲突**
   - `AWS_ACCESS_KEY_ID` 等环境变量设置错误
   - 多个凭证源冲突

### AWS 凭证优先级

```
1. 显式传递的凭证 (boto3.client(..., aws_access_key_id=...))
   ↓ (如果没有)
2. 环境变量
   - AWS_ACCESS_KEY_ID
   - AWS_SECRET_ACCESS_KEY
   - AWS_SESSION_TOKEN (临时凭证)
   ↓ (如果没有)
3. ~/.aws/credentials 文件
   - [default] 或指定的 profile
   ↓ (如果没有)
4. ~/.aws/config 文件
   - assume_role 配置
   ↓ (如果没有)
5. EC2 Instance Profile (如果在 EC2 上运行)
   - 自动从元数据服务获取
```

### 诊断方法

```bash
# 1. 测试凭证
aws sts get-caller-identity

# 成功输出:
# {
#     "UserId": "AIDXXXXXXXXXXXXXXXXX",
#     "Account": "399683337364",
#     "Arn": "arn:aws:iam::399683337364:user/xxx"
# }

# 失败输出:
# An error occurred (InvalidClientTokenId) ...

# 2. 检查凭证来源
aws configure list

# 3. 检查环境变量
env | grep AWS

# 4. 检查凭证文件
cat ~/.aws/credentials
cat ~/.aws/config
```

### 解决方案

#### 方案 1: 重新配置凭证

```bash
aws configure

# 输入新的凭证
AWS Access Key ID [****************XXXX]: your-new-access-key
AWS Secret Access Key [****************XXXX]: your-new-secret-key
Default region name [us-west-2]: us-west-2
Default output format [json]: json
```

#### 方案 2: 使用不同的 Profile

```bash
# 配置新的 profile
aws configure --profile galaxy-cloud

# 使用 profile
export AWS_PROFILE=galaxy-cloud

# 或者在命令中指定
aws s3 ls --profile galaxy-cloud
```

#### 方案 3: 使用环境变量

```bash
export AWS_ACCESS_KEY_ID="your-access-key"
export AWS_SECRET_ACCESS_KEY="your-secret-key"
export AWS_DEFAULT_REGION="us-west-2"

# 验证
aws sts get-caller-identity
```

### 使用诊断脚本

```bash
bash lib/galaxy/galaxy-cloud-executor/scripts/check_aws_credentials.sh
```

**脚本输出**:
```
====================================================================
  AWS 凭证检查
====================================================================

✅ AWS CLI 已安装
✅ AWS Access Key ID: AKIA****************
✅ AWS Secret Access Key: **********************
✅ Default Region: us-west-2
✅ AWS 凭证有效
账户 ID: 399683337364
```

### 预防措施

1. **使用长期凭证**
   - 创建 IAM User 和永久 Access Key
   - 定期轮换 (90天)

2. **使用 IAM Instance Profile** (推荐)
   - 如果在 EC2 上运行 Galaxy
   - 自动获取和刷新凭证

3. **凭证管理最佳实践**
   - 不要将凭证硬编码在代码中
   - 使用 AWS Secrets Manager 或 Parameter Store
   - 设置凭证过期告警

## 问题5: 容器 S3 访问被拒绝

### 问题现象

**症状**:
1. 作业成功提交到 AWS Batch
2. 作业状态: RUNNABLE → STARTING → RUNNING
3. 作业状态变为 FAILED
4. **在 CloudWatch Logs 中看到**:

```
fatal error: An error occurred (403) when calling the HeadObject operation: Forbidden
```

或:
```
botocore.exceptions.ClientError: An error occurred (AccessDenied) when calling the GetObject operation: Access Denied
```

### 根本原因

**IAM 角色的两个层次**:

```
┌─────────────────────────────────────────────────┐
│           EC2 Instance                          │
│                                                 │
│  ┌─────────────────────────────────────────┐  │
│  │  ECS Agent                              │  │
│  │  使用: ecsInstanceRole                  │  │
│  │  权限: 注册到 ECS, 拉取镜像              │  │
│  └─────────────────────────────────────────┘  │
│                                                 │
│  ┌─────────────────────────────────────────┐  │
│  │  Container (Galaxy 工具)                │  │
│  │  使用: BatchJobRole ⚠️                  │  │
│  │  权限: 访问 S3, CloudWatch Logs         │  │
│  └─────────────────────────────────────────┘  │
│                                                 │
└─────────────────────────────────────────────────┘
```

**关键理解**:
- **ecsInstanceRole**: EC2 实例的角色，用于管理容器
- **BatchJobRole**: **容器内部**的角色，用于访问 AWS 服务

**问题**:
- 容器需要访问 S3（上传/下载数据）
- 如果没有配置 BatchJobRole，容器**没有任何 IAM 权限**
- 导致 S3 操作被拒绝

### 数据流和权限

```
Galaxy (上传输入数据)
  ↓
S3: s3://bucket/input/data.fastq
  ↓ (容器需要 GetObject 权限)
Container 下载数据
  ↓ (容器内工具处理)
FastQC 运行
  ↓
Container 生成输出
  ↓ (容器需要 PutObject 权限)
S3: s3://bucket/output/result.html
  ↓
Galaxy (下载输出数据)
```

**每一步都需要正确的 IAM 权限！**

### 诊断方法

#### 步骤 1: 检查 Job Definition

```bash
# 列出最近的作业
RECENT_JOB=$(aws batch list-jobs \
  --job-queue galaxy-cloud-queue \
  --job-status FAILED \
  --max-results 1 \
  --query 'jobSummaryList[0].jobId' \
  --output text)

# 查看作业详情
aws batch describe-jobs --jobs "$RECENT_JOB" \
  --query 'jobs[0].container.jobRoleArn'

# 如果输出为 null，说明没有配置 Job Role
```

#### 步骤 2: 检查 CloudWatch Logs

```bash
# 获取日志流名称
LOG_STREAM=$(aws batch describe-jobs --jobs "$RECENT_JOB" \
  --query 'jobs[0].container.logStreamName' \
  --output text)

# 查看日志
aws logs get-log-events \
  --log-group-name /aws/batch/job \
  --log-stream-name "$LOG_STREAM" \
  --query 'events[*].message' \
  --output text

# 查找 403 或 AccessDenied 错误
```

#### 步骤 3: 验证 BatchJobRole 存在

```bash
# 检查角色
aws iam get-role --role-name BatchJobRole

# 检查 S3 策略
aws iam list-role-policies --role-name BatchJobRole
```

### 解决方案

#### 步骤 1: 创建 BatchJobRole

```bash
# 使用提供的脚本
bash lib/galaxy/galaxy-cloud-executor/scripts/create_job_role.sh

# 或手动创建
# (参考 03-AWS基础设施搭建实战指南.md)
```

#### 步骤 2: 验证 S3 权限

```bash
# 获取策略文档
aws iam get-role-policy \
  --role-name BatchJobRole \
  --policy-name BatchJobS3Access

# 应该包含:
# - s3:GetObject
# - s3:PutObject
# - s3:ListBucket
# - s3:DeleteObject
```

#### 步骤 3: 在 Job Definition 中配置

**在代码中** (如 `test_workflow_simple.py`):

```python
# 获取 Job Role ARN
job_role_arn = os.getenv('AWS_BATCH_JOB_ROLE_ARN', '')

# 构建 container properties
container_props = {
    'image': 'public.ecr.aws/amazonlinux/amazonlinux:latest',
    'vcpus': 1,
    'memory': 512,
    'command': ['bash', '-c', 'aws s3 ls']
}
```

## 问题6: Galaxy UI 无法显示日志

### 问题现象

**症状**:
1. 作业在 AWS Batch 成功完成 (SUCCEEDED)
2. Galaxy UI 显示作业成功 (绿色)
3. **但是点击 (i) 查看详情时，stdout 和 stderr 都是空的**
4. CloudWatch Logs 中**有**日志

### 根本原因

**代码层面的 Bug**:

在 `galaxy_cloud/galaxy_workflow/galaxy_job_runner.py` 第 360 行:

```python
# ❌ 错误的代码:
job_wrapper.finish("", "")  # 传递空字符串!

# ✅ 正确的代码:
job_wrapper.finish(result.stdout or "", result.stderr or "")  # 传递实际日志
```

**日志流程**:

```
Container 输出
  ↓ (自动捕获)
CloudWatch Logs
  ↓ (AWSBatchExecutor._get_job_logs())
result.stdout = "..."
result.stderr = "..."
  ↓ (galaxy_job_runner.py)
job_wrapper.finish(???, ???)  ⚠️ 这里传什么？
  ↓
Galaxy 数据库
  ↓
Galaxy UI
```

**Bug 的影响**:
- 日志成功检索到 `result.stdout` 和 `result.stderr`
- 但是 `job_wrapper.finish()` 传递的是空字符串
- Galaxy 数据库存储的是空字符串
- 用户看不到任何日志

### 诊断方法

#### 步骤 1: 验证 CloudWatch 有日志


### 解决方案

#### 修复代码

```bash
cd lib/galaxy/galaxy-cloud-executor

# 编辑文件
vim galaxy_cloud/galaxy_workflow/galaxy_job_runner.py

# 找到第 360 行附近
# 将:
#     job_wrapper.finish("", "")
# 改为:
#     job_wrapper.finish(result.stdout or "", result.stderr or "")

# 保存退出
```

**完整的修复**:

```python
# galaxy_job_runner.py 第 350-365 行

async def _finish_job(self, job_wrapper, result):
    """Complete job execution."""
    try:
        if result.status == 'succeeded':
            # ✅ 正确: 传递实际的 stdout 和 stderr
            job_wrapper.finish(
                result.stdout or "",  # 如果为 None,使用空字符串
                result.stderr or ""
            )
        else:
            job_wrapper.fail(
                result.stderr or "Job execution failed",
                result.stdout or ""
            )
    except Exception as e:
        logger.error(f"Error finishing job: {e}")
        job_wrapper.fail(str(e))
```

```bash
# 在 Galaxy UI 中运行 FastQC

# 查看作业详情
# 应该能看到 stdout 和 stderr 的内容
```

### 为什么会出现这个 Bug？

**可能的原因**:

1. **占位符代码**
   - 开发时先用空字符串占位
   - 忘记替换为实际日志

2. **复制粘贴错误**
   - 从其他 runner 复制代码
   - 没有适配云执行的逻辑

3. **测试不充分**
   - 只测试了作业执行成功
   - 没有验证日志是否正确显示

### 预防措施

1. **代码审查**
   - 关键方法需要审查
   - 特别是 finish/fail 相关逻辑

2. **集成测试**
   - 测试不仅要验证作业成功
   - 还要验证日志正确显示

3. **文档记录**
   - 记录已知 Bug 和修复
   - 帮助其他人避免
